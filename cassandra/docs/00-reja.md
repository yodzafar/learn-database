# Cassandra rejasi: wide-column model, query-first modellashtirish, consistency va ekspluatatsiya

Nima uchun alohida va muhim: Apache Cassandra yozish yuklamasi juda katta, geografik taqsimlangan va "hech qachon to'xtamasligi kerak" bo'lgan tizimlarning standart tanlovi (Apple, Netflix, Discord tarixi, Uber, telekom va IoT). U relational va document DB'lardan tubdan farq qiladi: leaderless ring, sozlanuvchan konsistentlik, LSM-tree storage, JOIN va ad-hoc so'rov yo'q, ma'lumot so'rovga qarab joylashtiriladi ("bitta so'rovga bitta jadval"). Cassandra'da eng ko'p xato modellashtirishda va tombstone, katta partition, repair kabi ekspluatatsiya masalalarida bo'ladi. Bu reja ichki tuzilishdan (write/read path, compaction) boshlab, CQL, modellashtirish, consistency, UDF/UDA va ekspluatatsiyagacha chuqur boradi; ScyllaDB ham shu yerda.

Boshlash: `theory/` dagi LSM-tree, consistent hashing, replication (leaderless), quorum, CAP/PACELC, gossip mavzulari oldin o'tilgan bo'lishi kerak, chunki bu yerda ularning Cassandra'dagi implementatsiyasi chuqur ko'riladi. `sql/` I–II bosqichi (CQL SQL'ga o'xshaydi va aynan shu o'xshashlik tuzoq). `mongodb/` III bosqichi (modellashtirish) bilan taqqoslash foydali, lekin shart emas.

Ishlash tartibi: `cassandra/docs/NN-nom.md` nazariya va vazifalar, kod `cassandra/NN-slug/main.cql` (`cqlsh -f` bilan), tekshiruv `test.cql` (kutilgan natijani `SELECT` bilan) yoki kerak bo'lganda `test.sh` (natijani `grep`/`diff` bilan solishtiradi). Klaster tajribalari (consistency, repair, node o'chishi) `main.sh` da `docker exec ldb-cassandra-N nodetool ...` buyruqlari bilan.

```
make up db=cassandra           # ldb-cassandra, bitta node (I–IV bosqich uchun yetarli)
make up db=cassandra-cluster   # 3 node'li klaster (ldb-cassandra-1..3), V bosqichdan
make shell db=cassandra        # interaktiv cqlsh
make cass n=05                 # cassandra/05-*/main.cql
make cass-test n=05            # cassandra/05-*/test.cql yoki test.sh
make reset db=cassandra
make check
```

Mac arm64 izohi: rasmiy `cassandra:5.0` image arm64 uchun mavjud. Cassandra JVM'i xotiraga ochko'z: 3 node'li klaster uchun Docker Desktop'ga kamida 6–8 GB RAM bering, compose'da `MAX_HEAP_SIZE`/`HEAP_NEWSIZE` kichik qilib qo'yilgan. Birinchi ishga tushish 1–2 daqiqa oladi, `nodetool status` da hamma node `UN` bo'lishini kuting. ScyllaDB tajribalari `make up db=scylla` (`scylladb/scylla` image, `--smp 1 --memory 1G`).

## Boshqa DBlar bilan solishtirish

| Mavzu | PostgreSQL / relational | Cassandra | MongoDB | DynamoDB |
|---|---|---|---|---|
| Model | jadval, normalizatsiya | wide-column: partition → tartiblangan qatorlar | hujjat | item, partition + sort key |
| So'rov tili | SQL, ad-hoc | CQL, faqat primary key bo'yicha samarali | MQL + aggregation | API, PartiQL |
| JOIN | bor | yo'q | `$lookup` | yo'q |
| Replikatsiya | leader-follower | leaderless, har node teng | replica set (leader) | boshqariladi, 3 AZ |
| Konsistentlik | kuchli | har so'rovda sozlanadi (ONE…ALL) | write/read concern | eventual yoki strong read |
| Tranzaksiya | to'liq ACID | LWT (Paxos), bitta partition; batch | multi-document | `TransactWriteItems` |
| Funksiya / procedura | PL/pgSQL, trigger | UDF/UDA (Java), Java trigger | `$function`, `$accumulator` | Streams + Lambda |
| Storage | B-tree + heap, WAL | LSM: commit log, memtable, SSTable | WiredTiger B-tree | boshqariladi (B-tree asosida) |
| O'chirish | darhol (MVCC + vacuum) | tombstone, gc_grace'dan keyin compaction | darhol | darhol, TTL asinxron |
| Kuchli tomoni | murakkab so'rov, integrity | yozish throughput, multi-DC, uptime | moslashuvchan model | serverless, boshqaruvsiz |

## I bosqich: Model va arxitektura
1. **Cassandra'ning kelib chiqishi va o'rni**: Amazon Dynamo (leaderless, consistent hashing, hinted handoff, read repair) va Google Bigtable (column family, memtable, SSTable) merosi, Facebook inbox search (2008), Apache loyihasi, 3.x, 4.0 (stabilizatsiya, audit, virtual tables), 4.1, 5.0 (SAI, vector search, trie memtable va SSTable, UCS, dynamic data masking, Java 17), wide-column (partitioned row store) atamasi va nima uchun "column-oriented" emas, Cassandra qachon to'g'ri (yozish ko'p, ma'lum so'rov naqshlari, time series, multi-DC, uptime) va qachon noto'g'ri (ad-hoc analytics, ko'p jadvalli tranzaksiya, kichik ma'lumot, tez-tez o'zgaruvchan so'rovlar), DataStax, ScyllaDB, Astra, Amazon Keyspaces, Azure Managed Instance for Cassandra
2. **Ring, token va gossip**: consistent hashing ring, partitioner (`Murmur3Partitioner` default, `RandomPartitioner`, `ByteOrderedPartitioner` va nima uchun hot spot), token va token range, vnodes (`num_tokens`, 4.0+ default 16, tokenlarni taqsimlash algoritmi `allocate_tokens_for_local_replication_factor`), gossip protokoli (har soniya, endpoint state, heartbeat, generation), failure detector (Phi Accrual), seed node'lar va ularning roli (faqat bootstrap), snitch (`SimpleSnitch`, `GossipingPropertyFileSnitch`, `Ec2Snitch`) va DC/rack xabardorligi, coordinator node tushunchasi, `nodetool ring`, `nodetool status` (UN/DN/UJ), `nodetool describering`, `nodetool getendpoints` bilan qaysi partition qaysi node'da ekanini topish
3. **Write path**: client → coordinator → replicalar, commit log (append-only, `commitlog_sync` periodic vs batch vs group, disk alohida bo'lishi), memtable (xotirada tartiblangan, 5.0 trie memtable), flush (memtable to'lganda yoki commit log chegarasida), SSTable (immutable fayl: `Data.db`, `Index.db`/`Partitions.db` va `Rows.db` 5.0 BTI formatida, `Summary.db`, `Filter.db`, `Statistics.db`, `CompressionInfo.db`, `TOC.txt`), nima uchun yozish juda tez (random I/O yo'q), upsert semantikasi (INSERT va UPDATE bir xil, read-before-write yo'q), timestamp bilan last-write-wins va soat sinxronizatsiyasi (NTP) muhimligi, `nodetool flush`, `sstablemetadata` va `sstabledump` bilan SSTable ichini ko'rish
4. **Read path va compaction**: bir nechta SSTable'dan birlashtirish, bloom filter (`bloom_filter_fp_chance`), partition key cache va row cache (qachon yoqish), partition index va summary (yoki 5.0 BTI trie index), compression offset, memtable + SSTable merge va timestamp bo'yicha g'olib, read amplification, compaction maqsadi (SSTable sonini kamaytirish, eski versiya va tombstone'larni tozalash), strategiyalar: SizeTiered (STCS, yozishga qulay, disk 2x), Leveled (LCS, o'qishga qulay, I/O ko'p), TimeWindow (TWCS, time series va TTL uchun, out-of-order yozish tuzog'i), Unified Compaction Strategy (UCS, 5.0, parametrlar bilan STCS va LCS orasida), `nodetool compactionstats`, `nodetool compact` (major compaction xavfi), `theory/` LSM bilan bog'lash

## II bosqich: CQL
5. **Keyspace va replikatsiya**: `CREATE KEYSPACE`, `SimpleStrategy` (faqat test) va `NetworkTopologyStrategy` (`{'dc1': 3, 'dc2': 3}`), replication factor tanlash (RF=3 standart va sababi), `ALTER KEYSPACE` va keyin `repair` majburiyligi, `durable_writes`, system keyspace'lar (`system`, `system_schema`, `system_auth`, `system_distributed`, `system_traces`, `system_views` virtual), `DESCRIBE`, cqlsh buyruqlari (`CONSISTENCY`, `TRACING`, `PAGING`, `EXPAND`, `COPY TO/FROM`, `SOURCE`, `CAPTURE`)
6. **Jadval va primary key**: `CREATE TABLE`, primary key = partition key + clustering columns, oddiy va composite partition key (`((a, b), c)`), clustering order (`WITH CLUSTERING ORDER BY (ts DESC)`), qatorlar partition ichida diskda tartiblangan saqlanishi, so'rov qoidalari: partition key to'liq tenglik bilan, clustering columns prefiks tartibida, oxirgi clustering column'da range, `IN` va uning coordinator narxi, `ORDER BY` faqat clustering bo'yicha, `LIMIT`, `PER PARTITION LIMIT`, `ALLOW FILTERING` nima qiladi va nima uchun production'da yomon (butun klaster skani), `TOKEN()` funksiyasi bilan to'liq skan (Spark connector shunday qiladi), jadval opsiyalari (`compaction`, `compression`, `gc_grace_seconds`, `default_time_to_live`, `caching`, `bloom_filter_fp_chance`, `speculative_retry`)
7. **Tiplar va collections**: native tiplar (`text`, `int`, `bigint`, `varint`, `decimal`, `double`, `boolean`, `uuid` va `timeuuid` farqi, `now()`, `minTimeuuid`/`maxTimeuuid`, `timestamp`, `date`, `time`, `duration`, `blob`, `inet`, `counter`), collections (`list`, `set`, `map`) va ular ichki qanday saqlanishi (har element alohida cell), list'da read-before-write qiladigan amallar (`list[index] = ...`, `-` operatori) va nima uchun set/map afzal, collection o'lchami chegarasi va katta collection anti-pattern'i, `frozen<>` (butun qiymat bitta cell, faqat to'liq almashtirish), UDT (`CREATE TYPE`, nested, frozen va non-frozen 3.6+), `tuple`, 5.0 `vector<float, n>` tipi, tip o'zgartirish cheklovlari
8. **INSERT, UPDATE, DELETE va vaqt**: INSERT va UPDATE ikkalasi upsert, `IF NOT EXISTS`/`IF EXISTS` (LWT, IV bosqichda chuqur), `USING TTL` va `USING TIMESTAMP`, `TTL()` va `WRITETIME()` funksiyalari (5.0 `MAXWRITETIME`), qator, ustun, range va partition darajasida DELETE, har DELETE tombstone yozishi, `null` qiymat INSERT qilish = tombstone (prepared statement'da unset vs null tuzog'i), TTL tugaganda ham tombstone hosil bo'lishi, static columns (partition darajasidagi qiymat, partition boshida saqlanadi), counter jadvallar (alohida jadval, faqat `UPDATE ... SET c = c + 1`, idempotent emasligi, aniqlik muammolari)
9. **Built-in funksiyalar va agregatlar**: skalyar funksiyalar (`token`, `uuid`, `now`, `toTimestamp`, `toDate`, `toUnixTimestamp`, `blobAsText`/`textAsBlob`, `CAST`), `writetime`/`ttl`, 5.0 matematik va collection funksiyalari (`abs`, `round`, `collection_count`, `collection_min` va h.k., faqat aniq versiyada mavjudlari), built-in agregatlar (`COUNT`, `MIN`, `MAX`, `SUM`, `AVG`) va ularning faqat bitta partition ichida ma'qulligi, `GROUP BY` (3.10+, faqat primary key ustunlari bo'yicha), `SELECT JSON`/`INSERT JSON`, `DISTINCT` partition key bo'yicha, `COUNT(*)` butun jadvalda nega xavfli (timeout), dynamic data masking 5.0 (`MASKED WITH mask_default()` va boshqa mask funksiyalari, `UNMASK` permission)

## III bosqich: Query-first modellashtirish
10. **Query-first metodologiya**: relational (entity-first, normalizatsiya) va Cassandra (query-first, denormalizatsiya) farqi, ish tartibi: konseptual model (ER) → ilova workflow va access patterns → mantiqiy model (Chebotko diagrammasi: Q1, Q2... va har biriga jadval) → fizik model (tiplar, o'lcham, opsiyalar), "bitta so'rovga bitta jadval" va yozishda bir nechta jadvalga yozish (denormalizatsiya narxi va izchilligi), nomlash konventsiyalari (`videos_by_user`, `users_by_email`), KillrVideo namunasi, relational sxemadan migratsiya mashqi
11. **Partition dizayni**: partition key tanlash: bir tekis taqsimot (hot partition'dan qochish) va so'rovni bitta partition'da bajarish o'rtasidagi muvozanat, partition o'lchami (qatorlar soni va bayt, tavsiya: 100 MB va 100 ming qatordan kam), o'lchamni oldindan hisoblash formulasi (Nv = Nr × (Nc − Npk − Ns) + Ns), bucketing (vaqt bo'yicha `day`, hash bucket, `(sensor_id, month)`), unbounded partition anti-pattern'i, wide partition va uning compaction, repair va heap'ga ta'siri, `nodetool tablehistograms` (eski `cfhistograms`) bilan partition o'lchamini o'lchash, large partition warning (`compaction_large_partition_warning_threshold`, 5.0 guardrails)
12. **Clustering va saralash patternlari**: clustering columns bilan "oxirgi N ta" so'rov (`DESC` order + `LIMIT`), time series modellashtirish (sensor, metrika, chat xabarlari: Discord tarixi), range so'rovlar, ko'p darajali clustering, lookup jadvallar (email → user_id), many-to-many ikki jadval bilan, versiyalash (`timeuuid` clustering), static columns bilan partition metadata, queue anti-pattern'i (tombstone bilan to'lgan partition) va uning o'rniga nima
13. **Tombstones va o'chirish dizayni**: tombstone turlari (cell, row, range, partition, TTL), nima uchun o'chirish = yozish, `gc_grace_seconds` (default 10 kun) va repair bilan bog'liqligi: repair qilinmagan node'da "zombie" (resurrected) ma'lumot, `tombstone_warn_threshold` va `tombstone_failure_threshold` (`TombstoneOverwhelmingException`), o'qishda tombstone skanining narxi, tombstone'ni kamaytiruvchi dizayn (TTL + TWCS, butun partition o'chirish, null yozmaslik, collection'ni to'liq almashtirmaslik), `sstablemetadata` dagi droppable tombstones, `nodetool garbagecollect`, `unchecked_tombstone_compaction`

## IV bosqich: Konsistentlik va tranzaksiyalar
14. **Consistency levels**: yozish va o'qish uchun alohida: `ANY` (hinted handoff bilan ham), `ONE`, `TWO`, `THREE`, `QUORUM`, `LOCAL_QUORUM`, `EACH_QUORUM`, `LOCAL_ONE`, `ALL`, `SERIAL`/`LOCAL_SERIAL` (LWT uchun), R + W > RF formulasi va kuchli konsistentlik, multi-DC'da `LOCAL_QUORUM` standart sababi, mavjudlik vs konsistentlik trade-off (PACELC), `UnavailableException` vs `WriteTimeoutException`/`ReadTimeoutException` farqi va ularni ilovada qanday ishlash (write timeout yozuv bo'lmagani degani emas), cqlsh `CONSISTENCY` bilan 3 node'li klasterda bitta node'ni to'xtatib tajriba, driver'da per-statement consistency
15. **Replikalarni tuzatish mexanizmlari**: hinted handoff (`max_hint_window`, default 3 soat, hint fayllar, `nodetool statushandoff`), read repair (blocking read repair QUORUM o'qishda, 4.0 da `read_repair_chance` olib tashlangan), anti-entropy repair (Merkle tree, full vs incremental repair, `nodetool repair -pr`, 4.0 dagi incremental repair tuzatishlari, subrange repair), repair jadvali va `gc_grace_seconds` ichida tugash shartligi, Cassandra Reaper, 5.0+ dagi avtomatik repair (faqat versiyada aniq mavjud bo'lsa), speculative retry, `theory/` dagi anti-entropy va Merkle tree bilan bog'lash
16. **Lightweight transactions**: compare-and-set (`IF NOT EXISTS`, `IF EXISTS`, `IF col = val`), Paxos protokoli (prepare/promise, read, propose/accept, commit: 4 round trip), `SERIAL` va `LOCAL_SERIAL` konsistentlik, `[applied]` ustuni, LWT narxi (latency 4x), LWT va oddiy yozuvni aralashtirish xavfi, 4.1 Paxos v2 yaxshilanishlari, unikallik (username registratsiyasi), optimistic locking (`version` ustuni), distributed lock va leader election (va ularning cheklovlari), Accord protokoli (CEP-15, general-purpose tranzaksiyalar) holati faqat aniq ma'lum bo'lsa
17. **Batches**: logged batch (batchlog, atomarlik kafolati, lekin izolyatsiya yo'q), unlogged batch, bir nechta denormalizatsiyalangan jadvalga bitta mantiqiy yozuvni atomar yozish (to'g'ri foydalanish), bulk load uchun multi-partition batch (anti-pattern: coordinator yuklamasi, `batch_size_warn_threshold`), bitta partition ichidagi batch (samarali), counter batch, batch va LWT birga (bitta partition sharti), batch ichida timestamp, async parallel yozuvlar bilan solishtirish

27. **Loyiha: IoT va messaging time series platforma**: sensor o'lchovlari va chat xabarlari uchun query-first model (Chebotko diagrammasi README'da), bucketed partition'lar va partition o'lchami hisobi, TWCS + TTL bilan retention, LWT bilan unikal username registratsiyasi, logged batch bilan denormalizatsiyalangan yozuv, UDA bilan partition ichidagi agregat, 3 node'li klasterda `LOCAL_QUORUM` bilan bitta node o'chganda ishlash isboti, repair va tombstone tahlili, `cassandra-stress` profil bilan p99 o'lchovi, README'da natijalar
28. **Migratsiya mashqi: relational'dan Cassandra'ga**: `postgres/` dagi kichik sxemani (buyurtmalar, foydalanuvchilar, mahsulotlar) access pattern'lardan boshlab Cassandra'ga qayta modellashtirish, har so'rovga jadval, yozish yo'lida izchillik strategiyasi (logged batch yoki idempotent qayta urinish), DSBulk yoki Spark bilan ma'lumot ko'chirish, ikki tizimda natijalarni solishtirish, "Cassandra bu yerda to'g'ri tanlovmi" degan xulosa

## Ataylab kiritilmagan
Thrift API va eski `cassandra-cli` (tarix sifatida qisqa), DSE (DataStax Enterprise) Search/Graph/Analytics chuqur, Cassandra manba kodiga hissa qo'shish, Kubernetes operatorlari chuqur (K8ssandra faqat eslatma; `ops/` modulida), JanusGraph (`graph/` modulida eslatma). Umumiy consistent hashing, quorum va LSM nazariyasi `theory/` da. Kerak bo'lsa alohida so'rang.

## Mezon
Har mavzu: `main.cql` `make cass n=NN` bilan xatosiz va idempotent ishlaydi (`IF NOT EXISTS`, `DROP ... IF EXISTS`), `test.cql`/`test.sh` natijani tekshiradi, modellashtirish vazifalarida Chebotko diagrammasi (matnli yoki mermaid) va partition o'lchami hisobi yozilgan, klaster vazifalarida `nodetool` chiqishi kommentda tahlil qilingan, har so'rov `ALLOW FILTERING` siz ishlaydi (alohida ko'rsatilgan joylardan tashqari), tracing bilan so'rov yo'li izohlangan. Loyihalar: README, partition hisobi, stress natijalari, failover isboti.
