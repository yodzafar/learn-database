# DynamoDB rejasi: access-pattern-first modellashtirish, single-table design va serverless arxitektura

Nima uchun alohida va muhim: Amazon DynamoDB AWS'dagi eng ko'p ishlatiladigan NoSQL va serverless arxitekturaning (Lambda, API Gateway, Step Functions) standart ma'lumot qatlami. U to'liq boshqariladi (server, patch, replikatsiya, masshtablash yo'q), istalgan hajmda bir xil bir xonali millisekund latency beradi, lekin buning narxi qat'iy: so'rov faqat kalit bo'yicha, JOIN yo'q, ad-hoc so'rov yo'q, va noto'g'ri model to'g'ridan-to'g'ri hisob-fakturada ko'rinadi. DynamoDB'da modellashtirish relational'ning teskarisi: avval barcha access pattern'lar, keyin kalitlar va indekslar, ko'pincha bitta jadvalga bir nechta entity (single-table design). Bu reja Dynamo merosidan boshlab, kalit dizayni, ifodalar, tranzaksiyalar, Streams + Lambda ("trigger va procedura" ekvivalenti), narx modeli va ekspluatatsiyagacha boradi; mashq DynamoDB Local'da, real AWS ixtiyoriy.

Boshlash: `cassandra/` I va III bosqichlari (partition key, query-first modellashtirish) DynamoDB'ni ancha osonlashtiradi, kamida `theory/` dagi partitioning, consistent hashing, replication va konsistentlik mavzulari shart. `mongodb/` III bosqichi (embed vs reference) bilan solishtirish foydali. AWS hisobi shart emas: hamma mashq `amazon/dynamodb-local` konteynerida, faqat Streams + Lambda va global tables uchun LocalStack yoki real AWS (Free Tier, budjet alarm bilan) ixtiyoriy.

Ishlash tartibi: `dynamodb/docs/NN-nom.md` nazariya va vazifalar, kod `dynamodb/NN-slug/main.sh` (`aws dynamodb ... --endpoint-url http://localhost:8000`, jadval va item'lar JSON fayllarda) yoki `main.py` (`boto3`, `endpoint_url` bilan; kerak bo'lsa Node.js `@aws-sdk/client-dynamodb` va `lib-dynamodb` ham mumkin, siz tanlaysiz), tekshiruv `test.sh` yoki `test_main.py`. DynamoDB Local uchun soxta kredensiallar (`AWS_ACCESS_KEY_ID=local`, `AWS_SECRET_ACCESS_KEY=local`, `AWS_REGION=us-east-1`) compose va Makefile'da beriladi, real kalitlar hech qachon kodda yoki git'da emas.

```
make up db=dynamodb           # ldb-dynamodb (amazon/dynamodb-local, port 8000, -sharedDb)
make up db=localstack         # ixtiyoriy: Streams + Lambda tajribalari uchun
make shell db=dynamodb        # aws cli muhiti endpoint bilan (yoki NoSQL Workbench'ni localhost:8000 ga ulang)
make ddb n=05                 # dynamodb/05-*/main.sh yoki main.py
make ddb-test n=05            # dynamodb/05-*/test.sh yoki test_main.py
make reset db=dynamodb
make check
```

## Boshqa DBlar bilan solishtirish

| Mavzu | PostgreSQL / relational | DynamoDB | Cassandra | MongoDB |
|---|---|---|---|---|
| Boshqaruv | o'zingiz yoki RDS | to'liq boshqariladi, serverless | o'zingiz (yoki Keyspaces, Astra) | o'zingiz yoki Atlas |
| Kalit | ixtiyoriy indekslar | partition key (+ sort key), GSI/LSI | partition key + clustering | `_id` + ixtiyoriy indekslar |
| So'rov | SQL, ad-hoc | `GetItem`, `Query`, `Scan`, PartiQL (cheklangan) | CQL, primary key bo'yicha | MQL, ad-hoc mumkin |
| JOIN | bor | yo'q, single-table design bilan "oldindan join" | yo'q | `$lookup` |
| Konsistentlik | kuchli | eventual (default) yoki strongly consistent read; GSI faqat eventual | sozlanadi | sozlanadi |
| Tranzaksiya | to'liq ACID | `TransactWriteItems`/`TransactGetItems` (100 item, 4 MB) | LWT | multi-document |
| Trigger / procedura | trigger, PL/pgSQL | Streams + Lambda, condition expressions | UDF/UDA, Java trigger | change streams, `$function` |
| Masshtablash | qo'lda | avtomatik partition bo'linishi | node qo'shish | sharding |
| Narx modeli | server/instance | so'rov birligi (RRU/WRU yoki RCU/WCU) + storage | server | server yoki Atlas tier |
| Item/hujjat chegarasi | qator ~1 GB (TOAST) | 400 KB | partition tavsiyasi ~100 MB | 16 MB |

## I bosqich: Asoslar va arxitektura
1. **Dynamo'dan DynamoDB'gacha**: Dynamo paper (2007: leaderless, consistent hashing, sloppy quorum, vector clock, hinted handoff) va DynamoDB (2012) farqi: DynamoDB leader-based (har partition uchun Multi-Paxos bilan saylangan leader, 3 AZ'da replikalar), vector clock va client tomonida konflikt hal qilish yo'q, boshqariladigan xizmat, 2022 USENIX ATC "Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service" maqolasi asosiy g'oyalari (request router, storage node, B-tree + replikatsiya log, partition bo'linishi, admission control, GAC: global admission control), DynamoDB qachon to'g'ri (ma'lum access pattern'lar, serverless, oldindan aytib bo'ladigan latency, katta masshtab) va qachon noto'g'ri (ad-hoc analytics, murakkab relational hisobot, tez o'zgaruvchan so'rovlar), Cassandra'ning Dynamo'dan olgan narsalari bilan solishtirish
2. **Jadval, item, atribut va kalitlar**: jadval, item (400 KB chegarasi, atribut nomlari ham hajmga kiradi), atribut tiplari (scalar: `S`, `N` (38 xonali aniqlik, string sifatida uzatiladi), `B`, `BOOL`, `NULL`; document: `M`, `L`; set: `SS`, `NS`, `BS`), DynamoDB JSON formati va SDK'dagi document client (marshalling, `lib-dynamodb`, `boto3.resource` vs `client`, `TypeDeserializer`), primary key: simple (partition key) va composite (partition key + sort key), partition key hash'lanib saqlanishi, sort key bo'yicha partition ichida tartib, item collection tushunchasi, kalit atributlar o'zgarmasligi (o'chirib qayta yozish), `CreateTable`, `DescribeTable`, `ListTables`, `DeleteTable`, `UpdateTable`, `aws dynamodb wait table-exists`
3. **Partitionlar, capacity va throughput**: ichki partition (taxminan 10 GB va 3000 RCU / 1000 WCU chegarasi), partition bo'linishi (split for size va split for heat), capacity modes: on-demand (so'rov uchun to'lov, RRU/WRU, oldingi cho'qqining ikki barobarigacha darhol masshtablash, 2024 yildagi on-demand narx pasayishi va maximum throughput sozlamasi) va provisioned (RCU/WCU, auto scaling target utilization bilan, reserved capacity), birliklar hisobi (1 RCU = 4 KB strongly consistent o'qish yoki 2 ta eventual; 1 WCU = 1 KB yozish; tranzaksiya 2x), burst capacity (300 soniya), adaptive capacity (issiq partition'ga throughput qayta taqsimlanishi, isolate frequently accessed items), hot partition va hot key muammosi (`ProvisionedThroughputExceededException`, throttling), write sharding (kalitga suffiks qo'shish), DynamoDB Local'da throughput simulyatsiya qilinmasligi va buni qanday hisobga olish

## II bosqich: API, ifodalar va so'rovlar
4. **Item amallari va o'qish konsistentligi**: `PutItem` (to'liq almashtirish), `GetItem` (`ConsistentRead`), `UpdateItem` (qisman yangilash), `DeleteItem`, `ReturnValues` (`ALL_OLD`, `UPDATED_NEW` va boshqalar), `ReturnConsumedCapacity` bilan har so'rov narxini o'lchash, `ReturnValuesOnConditionCheckFailure`, eventual vs strongly consistent read (leader'dan o'qish, narxi 2x, GSI'da strong yo'q), batch amallar (`BatchGetItem` 100 item / 16 MB, `BatchWriteItem` 25 put/delete, `UnprocessedKeys`/`UnprocessedItems` va exponential backoff bilan qayta urinish, batch tranzaksiya emasligi), SDK retry siyosati va idempotentlik
5. **Expressions: key condition, filter, projection**: expression atribut nomlari (`ExpressionAttributeNames`, `#name`, reserved words ro'yxati tuzog'i) va qiymatlari (`ExpressionAttributeValues`, `:val`), `KeyConditionExpression` (partition key tenglik + sort key: `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `begins_with`), `FilterExpression` (o'qilgandan keyin filtrlaydi: capacity baribir sarflanadi, `Limit` filtrdan oldin qo'llanadi tuzog'i), `ProjectionExpression` (nested atribut va list indeks: `a.b[0]`), funksiyalar (`attribute_exists`, `attribute_not_exists`, `attribute_type`, `begins_with`, `contains`, `size`), `IN`, mantiqiy operatorlar
6. **Condition va update expressions (server tomonidagi logika)**: `ConditionExpression` bilan shartli yozish (`attribute_not_exists(PK)` bilan "faqat yaratish", qiymat tekshiruvi bilan biznes qoida), `ConditionalCheckFailedException` va uni ilovada ishlash, optimistic locking (`version` atributi, shart `version = :expected`, `SET version = version + :one`), `UpdateExpression` amallari: `SET` (`if_not_exists`, `list_append`, arifmetika `a = a + :n`), `REMOVE` (atribut va list elementi), `ADD` (son va set uchun atomar), `DELETE` (set'dan element), atomar hisoblagich va uning idempotent emasligi, nested map'ni yangilash va mavjud bo'lmagan oraliq map xatosi, "server tomonda shart bilan bitta atomar o'zgartirish": DynamoDB'da stored procedure'ning eng yaqin ekvivalenti
7. **Query, Scan va pagination**: `Query` (bitta item collection ichida, sort key bo'yicha tartib, `ScanIndexForward`, `Limit`), 1 MB javob chegarasi va `LastEvaluatedKey`/`ExclusiveStartKey` bilan pagination, sahifa raqami yo'qligi va cursor'ni clientga xavfsiz berish (shifrlash yoki imzolash), `Select: COUNT`, `Scan` (butun jadval, qimmat, qachon oqlanadi: kichik jadval, eksport, bir martalik migratsiya), parallel scan (`Segment`, `TotalSegments`), sparse indeks bilan Scan'dan qochish, `Query` vs `Scan` narx hisobi `ReturnConsumedCapacity` bilan, PartiQL (`ExecuteStatement`, `BatchExecuteStatement`, `ExecuteTransaction`: SQL'ga o'xshash sintaksis, lekin `WHERE` kalitsiz bo'lsa yashirin full scan tuzog'i, IAM bilan full scan'ni taqiqlash)

## III bosqich: Modellashtirish
8. **Access-pattern-first metodologiya**: relational (entity → normalizatsiya → ad-hoc so'rov) va DynamoDB (access pattern'lar ro'yxati → kalit dizayni) farqi, ish tartibi: ER diagramma, access pattern jadvali (har pattern: nima, qanday parametr, qancha tez-tez, qanday tartib), entity chart, kalitlarni loyihalash, har pattern uchun `GetItem`/`Query` aniqlash, "Scan kerak bo'lsa model xato" qoidasi, kalit nomlash konventsiyalari (`PK`/`SK` umumiy nomlar, `USER#123`, `ORDER#2025-01-01#456`), sort key'da ierarxiya (`COUNTRY#UZ#CITY#TASHKENT`) va `begins_with` bilan so'rov, NoSQL Workbench bilan vizual modellashtirish va DynamoDB Local'ga commit qilish
9. **Secondary indekslar: GSI va LSI**: Global Secondary Index (boshqa partition key, o'z capacity'si, asinxron va eventual, 20 ta default chegarasi, kalit atributi yo'q item'lar indeksga tushmasligi), Local Secondary Index (bir xil partition key, boshqa sort key, faqat jadval yaratishda, strong read mumkin, 10 GB item collection chegarasi), projection turlari (`KEYS_ONLY`, `INCLUDE`, `ALL`) va narx/hajm trade-off, GSI throttling'ning asosiy jadvalga back-pressure qilishi, sparse index patterni (faqat ma'lum holatdagi item'lar: "ochiq buyurtmalar"), GSI overloading (bitta GSI'da `GSI1PK`/`GSI1SK` bilan bir nechta pattern), inverted index (many-to-many uchun PK va SK almashtirilgan GSI), GSI'ni keyinroq qo'shish (backfill) narxi
10. **Single-table design**: nima uchun bitta jadval (bitta so'rovda bir nechta entity: "pre-joined" item collection, kam round-trip, Rick Houlihan re:Invent chiqishlari), one-to-many patternlari (denormalizatsiya: complex atribut ichida, atributlarni nusxalash, composite primary key item collection, secondary index, composite sort key), many-to-many (adjacency list patterni va inverted index), ierarxik ma'lumot, vaqt bo'yicha tartib (KSUID/ULID sort key'da), bir nechta entity uchun `Type` atributi, single-table'ning salbiy tomonlari (o'rganish egri chizig'i, analytics va eksport qiyinligi, yangi access pattern qo'shish narxi, GraphQL resolver'lar bilan muvofiqlik), multi-table qachon to'g'ri (Alex DeBrie'ning "single-table vs multi-table" fikri, AppSync/Amplify misoli), relational sxemani (e-commerce yoki SaaS) single-table'ga ko'chirish mashqi
11. **Murakkab patternlar va migratsiya**: write sharding (`PK#<0–N>` scatter-gather bilan o'qish), hisoblagichlar va agregatlar (oldindan hisoblash, Streams orqali yangilash), unikallik cheklovi (ikkinchi atribut uchun alohida "guard" item va tranzaksiya), leaderboard va "top-N" (GSI + sort key), TTL bilan vaqtinchalik ma'lumot (session, OTP), katta ob'ektlar (S3'da saqlab DynamoDB'da pointer), versiyalash va audit tarix (`v0` joriy + `v1..vN` tarix item'lari), sxema evolyutsiyasi va backfill (Scan + update, Step Functions distributed map yoki EMR/Glue), yangi access pattern qo'shishning to'rt yo'li (yangi GSI, mavjud GSI overload, yangi atribut va backfill, alohida jadval), ORM/ODM'lar (ElectroDB, DynamoDB Toolbox, PynamoDB, Dynamoose) va ularning foydasi/xavfi

## IV bosqich: Tranzaksiyalar va hodisalar
12. **Transactions**: `TransactWriteItems` (`Put`, `Update`, `Delete`, `ConditionCheck`; 100 ta amal va 4 MB gacha, bir nechta jadval bo'ylab), `TransactGetItems`, serializable izolyatsiya tranzaksiyalar orasida va read-committed tranzaksiyadan tashqari o'qishlar uchun, narxi (har item uchun 2x capacity), `ClientRequestToken` bilan idempotentlik (10 daqiqa), `TransactionCanceledException` va `CancellationReasons`ni o'qish, `TransactionConflictException`, bir item'ga bir tranzaksiyada faqat bitta amal, pul o'tkazish, unikal username, inventar zaxira misollari, global tables'da tranzaksiya faqat bitta region ichida, relational ACID va MongoDB transaction bilan solishtirish
13. **DynamoDB Streams va Lambda (trigger va procedura ekvivalenti)**: Streams yoqish va `StreamViewType` (`KEYS_ONLY`, `NEW_IMAGE`, `OLD_IMAGE`, `NEW_AND_OLD_IMAGES`), 24 soatlik retention, shard'lar va item darajasida tartib kafolati, Lambda event source mapping (`BatchSize`, `MaximumBatchingWindowInSeconds`, `ParallelizationFactor`, `StartingPosition`, `BisectBatchOnFunctionError`, `MaximumRetryAttempts`, `DestinationConfig` on-failure SQS/SNS, event filtering `FilterCriteria`), at-least-once va idempotent handler (Powertools idempotency), patternlar: agregatlarni yangilash, materialized view, OpenSearch'ga indekslash, outbox va event-driven integratsiya (EventBridge Pipes), audit log, cross-region yoki cross-account replikatsiya, Kinesis Data Streams for DynamoDB (uzunroq retention, ko'p iste'molchi) bilan farqi, LocalStack yoki real AWS'da mashq, relational trigger va stored procedure'ni "yozishda shart (condition expression) + yozishdan keyin hodisa (Streams + Lambda)" ga ajratish
14. **TTL va hayot sikli**: TTL atributi (epoch sekund, `Number` tipi), asinxron o'chirish (odatda bir necha kun ichida, aniq vaqt kafolati yo'q, shuning uchun o'qishda ham filtrlash kerak), TTL o'chirishi WCU sarflamasligi, Streams'da TTL o'chirishlari `userIdentity` bilan ajralishi va ularni S3 arxivga yuborish patterni, session, cache, OTP va vaqtinchalik qulf uchun TTL, ma'lumot retention siyosati va GDPR o'chirish talabi

## V bosqich: Ekspluatatsiya, xavfsizlik va narx
15. **Global tables, DAX, backup va eksport**: global tables (multi-region, multi-active, version 2019.11.21, last-writer-wins konflikt hal qilish, replikatsiya kechikishi, 2024+ multi-region strong consistency imkoniyati faqat aniq versiya/region holatini tekshirib), DAX (in-memory kesh klasteri, item cache va query cache, write-through, eventual consistency, qachon kerak va qachon ElastiCache/Redis yaxshiroq), backup: on-demand backup va PITR (35 kungacha, sekund aniqligida tiklash yangi jadvalga), AWS Backup, export to S3 (PITR asosida, DynamoDB JSON yoki Ion formatida, jadvalga yuk tushirmasdan) va incremental export, import from S3, Athena/Glue/Redshift bilan analytics (`data-engineering/` havola), zero-ETL integratsiyalari (OpenSearch, Redshift) faqat aniq bilgan holda
16. **Xavfsizlik va kuzatuv**: IAM (`dynamodb:GetItem` va boshqa action'lar, resource ARN jadval va indeks uchun), fine-grained access control (`dynamodb:LeadingKeys` sharti bilan foydalanuvchi faqat o'z partition'ini ko'rishi, `dynamodb:Attributes`), resource-based policy (2024+), VPC endpoint, encryption at rest (AWS owned, AWS managed, customer managed KMS key), deletion protection, CloudTrail (control plane va data plane eventlari), CloudWatch metrikalari (`ConsumedReadCapacityUnits`, `ThrottledRequests`, `SuccessfulRequestLatency`, `SystemErrors`, `UserErrors`), Contributor Insights (eng issiq kalitlar), alarm'lar, SDK sozlamalari (timeout, retry, keep-alive, connection reuse Lambda'da), X-Ray bilan tracing
17. **Narx modellashtirish va IaC**: narx komponentlari (o'qish/yozish birliklari, storage, GSI, Streams o'qish, backup/PITR, global tables replicated write, DAX, data transfer, Standard vs Standard-Infrequent Access table class), on-demand vs provisioned qarori (yuklama profili, utilization), item hajmini kamaytirish (qisqa atribut nomlari, siqish, katta qismni S3'ga), `ReturnConsumedCapacity` bilan har access pattern narxini o'lchab oylik hisob jadvali tuzish, AWS Pricing Calculator, IaC: CloudFormation/CDK, Terraform (`aws_dynamodb_table`) va SAM bilan jadval, GSI, Streams va Lambda'ni kod sifatida yozish, lokal va prod muhitlar uchun bir xil ta'rif, Amazon Keyspaces va ScyllaDB Alternator (DynamoDB-mos API) haqida qisqa eslatma

## VI bosqich: Loyiha
18. **Loyiha: serverless SaaS backend uchun single-table model**: kichik ko'p tenant'li SaaS (tashkilot, foydalanuvchi, loyiha, vazifa, izoh) uchun 10–12 access pattern jadvali, NoSQL Workbench modeli va README'da entity chart, single-table + 1–2 GSI (overloading, sparse index), condition expression bilan biznes qoidalar va optimistic locking, `TransactWriteItems` bilan unikal email, cursor pagination (imzolangan `LastEvaluatedKey`), TTL bilan taklif havolalari, Streams + Lambda (LocalStack yoki real AWS) bilan agregat hisoblagichlar va idempotent handler, fine-grained IAM siyosati tenant bo'yicha (hujjatda), har access pattern uchun `ReturnConsumedCapacity` natijasi va oylik narx hisobi, `boto3`/SDK bilan testlar DynamoDB Local'da, IaC (CDK yoki Terraform) ta'rifi

## Ataylab kiritilmagan
DynamoDB ichki implementatsiyasining hujjatlanmagan tafsilotlari, Amazon Keyspaces chuqur (`cassandra/` da eslatma), AppSync/GraphQL resolver yozish chuqur, AWS sertifikatsiya imtihoniga maxsus tayyorgarlik, real AWS'da katta yuklama testlari (xarajat). Umumiy partitioning va replikatsiya nazariyasi `theory/` da, Streams'dan keyingi analytics pipeline'lar `data-engineering/` da. Kerak bo'lsa alohida so'rang.
