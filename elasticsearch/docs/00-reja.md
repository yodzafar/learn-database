# Elasticsearch rejasi: qidiruv tizimi, Lucene ichki tuzilishi va analytics

Nima uchun alohida: Elasticsearch ma'lumotlar bazasi emas, qidiruv tizimi (search engine). U relevance (eng mos natija), full-text qidiruv, fasetli filtr, autocomplete, log va metrikalar analytics'i uchun yaratilgan. Relational baza "aynan shu qatorni top" savoliga javob beradi, Elasticsearch esa "bu so'rovga eng mos hujjatlar qaysi va nima uchun" savoliga. Deyarli har katta mahsulotda (e-commerce qidiruvi, log platformasi, SIEM, observability) u yoki uning fork'i OpenSearch bor. Frontend'dan kelgan dasturchi uchun bu eng tez "ko'zga ko'rinadigan" natija beradigan DB: qidiruv qutisi, autocomplete, filtrlar to'g'ridan-to'g'ri UI ga ulanadi.

Litsenziya tarixi (tanlovga ta'sir qiladi): 2021-yilda Elastic Apache 2.0 dan SSPL va Elastic License 2.0 ga o'tdi, bunga javoban AWS OpenSearch fork'ini yaratdi (Apache 2.0, hozir Linux Foundation qoshidagi OpenSearch Software Foundation'da). 2024-yilda Elastic uchinchi variant sifatida AGPLv3 ni qo'shdi. Bu rejada asosiy versiya Elasticsearch 8.x (9.x farqlari alohida aytiladi), OpenSearch farqlari 22-mavzuda.

Boshlash: `theory/` dagi inverted index mavzusi (nazariya o'sha yerda, bu yerda amaliy ichki tuzilish), `sql/` I bosqich (filtr, aggregatsiya, `GROUP BY` tushunchasi). JSON va HTTP/REST yaxshi tanish deb hisoblanadi.

Ishlash tartibi: `elasticsearch/docs/NN-nom.md` nazariya va vazifalar, kod `elasticsearch/NN-slug/main.sh` (curl so'rovlar ketma-ketligi, `scripts/es.sh` helper: `es GET /_cat/indices?v`, `es PUT /products @mapping.json`). Katta JSON tanalar alohida `*.json` fayllarda. Tekshiruv `test.sh` da (`jq` bilan javobni tasdiqlash: hit soni, birinchi natija id si, aggregatsiya qiymati). Konteyner `ldb-elasticsearch` (single-node, security o'chirilgan lokal mashq uchun; 21-mavzuda yoqiladi), Kibana ixtiyoriy `ldb-kibana` (Dev Tools). Buyruqlar: `make up db=elasticsearch`, `make shell db=elasticsearch`, `make es n=01`, `make es-test n=01`, `make reset db=elasticsearch`.

## Boshqa DBlar bilan solishtirish

| Mavzu | PostgreSQL | MongoDB | Elasticsearch |
|---|---|---|---|
| Asosiy model | jadval, qator | hujjat (BSON) | hujjat (JSON), inverted index ustida |
| Full-text | `tsvector`, GIN, oddiy ranking | `$text`, Atlas Search (Lucene) | asosiy vazifa, BM25, analyzer zanjiri |
| Tranzaksiya | to'liq ACID | multi-document ACID | yo'q, faqat hujjat darajasida atomar |
| Konsistentlik | darhol | sozlanadi | near real-time (refresh, odatda 1s) |
| Sxema | qat'iy | ixtiyoriy | mapping, maydon tipi keyin o'zgarmaydi (reindex) |
| JOIN | to'liq | `$lookup` | deyarli yo'q (`nested`, `join` field, denormalizatsiya) |
| Aggregatsiya | `GROUP BY`, aniq | pipeline, aniq | bucket/metric, ba'zilari taxminiy (`cardinality`, `terms`) |
| Procedura ekvivalenti | PL/pgSQL | `$function` (eskirgan) | Painless script, ingest pipeline |
| Asosiy rol | source of truth | source of truth | odatda ikkilamchi indeks (asosiy DB dan sinxron) |

## I bosqich: Asoslar va ichki tuzilish

1. **Search engine va DB farqi**: qidiruv tizimi nima uchun alohida (relevance, tokenizatsiya, fuzzy, fasetlar), Elasticsearch qachon kerak (full-text, autocomplete, log/metrics analytics, geo) va qachon kerak emas (source of truth, tranzaksiya, kuchli konsistentlik, tez-tez yangilanadigan counter), "Postgres FTS yetarlimi" savoli (hajm, relevance sozlash, analyzer), arxitektura patterni: asosiy DB + sinxronlash (dual write tuzog'i, CDC/Debezium, outbox, bulk reindex), Elastic Stack (Elasticsearch, Kibana, Logstash, Beats, Elastic Agent), litsenziya tarixi (2021 SSPL/ELv2, OpenSearch fork, 2024 AGPL), versiyalar (7.x da type'lar olib tashlangan, 8.x da security default yoqilgan, 9.x), konteynerda single-node ishga tushirish (`discovery.type=single-node`, `xpack.security.enabled=false`, `ES_JAVA_OPTS` heap), birinchi so'rovlar: `GET /`, `GET /_cluster/health`, `GET /_cat/nodes?v`, `PUT /idx/_doc/1`, `GET /idx/_search`
2. **REST API va asosiy CRUD**: index, document, `_id`, `_source`, `_version`, `_seq_no`/`_primary_term` (optimistic concurrency, `if_seq_no`/`if_primary_term`), `PUT` vs `POST` (`_doc`, `_create`), `GET`/`HEAD`/`DELETE`, `_update` (partial doc, `doc_as_upsert`, `upsert`, script bilan), `_mget`, `_bulk` NDJSON formati (har qatorda action va manba, oxirida `\n`, xato qisman bo'lishi: `errors: true` va har item tekshirish), `refresh` parametri (`true`/`wait_for`/`false`) va near real-time ma'nosi, `_cat` API'lar (`indices`, `shards`, `health`, `count`), Kibana Dev Tools konsoli va curl ekvivalenti, `?pretty`, `filter_path` bilan javobni qisqartirish, `scripts/es.sh` helper yozish, HTTP status kodlari va xato tuzilmasi (`error.root_cause`)
3. **Lucene ichki tuzilishi**: inverted index (term dictionary, postings list, term frequency, positions, offsets), FST (finite state transducer) term dictionary uchun, segment (immutable), yangi hujjat avval in-memory buffer va translog ga, `refresh` = yangi segment ochish (qidiruvga ko'rinadi), `flush` = Lucene commit va translog tozalash, segment merge (nega delete darhol joy bo'shatmaydi: `.liv` deleted docs bitset, merge vaqtida haqiqiy o'chish), `_forcemerge` qachon (faqat read-only indeksda), doc values (columnar, diskda, sort/aggregatsiya uchun) va fielddata (heap'da, `text` ustida, nega xavfli), BKD tree (son, sana, geo, `ip` uchun range), stored fields va `_source` (compression), norms, `GET /idx/_segments`, `_stats`, "update = delete + insert" va uning narxi, translog `durability` (`request` vs `async`)
4. **Cluster arxitekturasi**: node rollari (`master`, `data`, `data_hot`/`data_warm`/`data_cold`/`data_frozen`, `ingest`, `ml`, `coordinating only`, `voting_only`), cluster state va master node vazifasi, master election (8.x da Raft'ga o'xshash algoritm, `cluster.initial_master_nodes`, quorum, voting configuration, nega 3 ta master-eligible node), split brain va 7.x dan oldingi `minimum_master_nodes` tarixi, primary va replica shard, shard soni index yaratilganda belgilanadi (`number_of_shards`, keyin `_split`/`_shrink`), replica soni dinamik, routing formulasi (`hash(_routing) % num_primary_shards`) va custom routing, so'rov qanday bajariladi (coordinating node: query phase va fetch phase, scatter-gather), yozish oqimi (primary ga, keyin replicalarga, `wait_for_active_shards`), cluster health (`green`/`yellow`/`red`) va nega single-node da `yellow`, shard allocation (`_cluster/allocation/explain`, awareness, filtering), 3 node'li klasterni docker compose da ko'tarish va node'ni o'chirib failover kuzatish

## II bosqich: Mapping va analysis

5. **Mapping chuqur**: dynamic mapping (nima uchun productionda xavfli: mapping explosion, noto'g'ri tip taxmini, `"123"` string vs son), `dynamic: strict`/`false`/`runtime`, explicit mapping, maydon tiplari (`text`, `keyword`, `long`/`integer`/`scaled_float`, `date` va `format`, `boolean`, `ip`, `geo_point`/`geo_shape`, `wildcard`, `match_only_text`, `search_as_you_type`, `dense_vector`, `flattened`), `text` vs `keyword` (tahlil qilinadi vs aynan qiymat, qachon qaysi), multi-fields (`fields: { raw: { type: keyword } }`), `index: false`, `doc_values: false`, `enabled: false`, `_source` va `includes`/`excludes`, `copy_to`, `null_value`, `ignore_above`, `ignore_malformed`, `coerce`, mavjud maydon tipini o'zgartirib bo'lmasligi va yechimi (yangi index + `_reindex` + alias), `index.mapping.total_fields.limit`, `GET /idx/_mapping`, `_field_caps`
6. **Murakkab ma'lumot: object, nested, flattened, join**: `object` tipi va array of objects muammosi (maydonlar "yassilanadi", cross-object match xatosi, misol bilan isbotlash), `nested` (alohida yashirin Lucene hujjat, `nested` query va aggregatsiya, narxi, `index.mapping.nested_objects.limit`), `flattened` (noma'lum kalitli metadata, cheklovlari), `join` field (parent/child, `has_child`/`has_parent`, nega sekin va kam ishlatiladi), denormalizatsiya qilish yoki application-side join, runtime fields (`runtime` mapping va so'rov ichida, `emit`, schema-on-read, qachon foydali, narxi), `_id` dizayni (tabiiy id vs avtomatik, idempotent ingestion uchun ahamiyati)
7. **Analysis zanjiri**: analyzer = `char_filter` + `tokenizer` + `filter` (token filter), `_analyze` API bilan har bosqichni ko'rish, built-in analyzerlar (`standard`, `simple`, `whitespace`, `keyword`, `stop`, `pattern`, til analyzerlari: `english`, `russian`), tokenizerlar (`standard`, `whitespace`, `pattern`, `uax_url_email`, `ngram`, `edge_ngram`, `path_hierarchy`), token filterlar (`lowercase`, `asciifolding`, `stop`, `stemmer`, `snowball`, `synonym`/`synonym_graph`, `shingle`, `word_delimiter_graph`, `unique`), char filterlar (`html_strip`, `mapping`, `pattern_replace`), index-time vs search-time analyzer (`search_analyzer`), normalizer `keyword` uchun (case-insensitive aniq qidiruv), custom analyzer `settings.analysis` da, analyzer o'zgarsa reindex kerak, o'zbek tili uchun (lotin/kirill: `icu` plugin, `icu_transform`/`asciifolding`, tutuq belgisi `'` va `ʻ` muammosi, stemmer yo'qligi va yechimlar)
8. **Autocomplete, synonyms va til masalalari**: autocomplete usullari taqqosi (`edge_ngram` index-time, `search_as_you_type` tipi, `completion` suggester (FST, juda tez, cheklangan), `match_bool_prefix`, `prefix` query narxi), typo tolerance (`fuzziness: AUTO`, Levenshtein, `prefix_length`), did-you-mean (`term`/`phrase` suggester), synonymlar (inline, fayl, synonyms API 8.10+, `synonym_graph` faqat search-time va nima uchun, multi-word synonym muammosi), stemming vs lemmatization, stop words zarari va foydasi, `ngram` ning index hajmiga ta'siri, transliteratsiya (kirill so'rov bilan lotin hujjatni topish), har usulning index hajmi va latency'sini o'lchash vazifasi

## III bosqich: Qidiruv va relevance

9. **Query DSL I: asosiy so'rovlar**: query context vs filter context (score hisoblanadi va keshlanmaydi vs score yo'q va keshlanadi), full-text (`match`, `match_phrase` va `slop`, `match_phrase_prefix`, `multi_match` turlari: `best_fields`/`most_fields`/`cross_fields`/`phrase`/`bool_prefix`, `query_string` va `simple_query_string` va nega `query_string` ni foydalanuvchiga ochmaslik), term-level (`term`, `terms`, `range`, `exists`, `prefix`, `wildcard`, `regexp`, `fuzzy`, `ids`), `term` ni `text` maydonda ishlatish tuzog'i (analyzer), `bool` (`must`, `filter`, `should`, `must_not`, `minimum_should_match`), `constant_score`, `match_all`/`match_none`, `_source` filtrlash, `fields`, `size`/`from`, `track_total_hits` (default 10000 chegarasi)
10. **Query DSL II: murakkab so'rovlar**: `nested` query va `inner_hits`, `has_child`/`has_parent`, geo so'rovlar (`geo_distance`, `geo_bounding_box`, `geo_shape`, distance bo'yicha sort), `dis_max` va `tie_breaker`, `boosting` (negative boost), `function_score` (`field_value_factor`, `decay` funksiyalari `gauss`/`exp`/`linear` sana va masofa uchun, `random_score`, `script_score`, `score_mode`/`boost_mode`), `rank_feature`/`distance_feature`, `percolate` (teskari qidiruv: saqlangan so'rovlarga hujjatni moslash, alert uchun), `highlight` (`unified`, `fvh`, fragment sozlash), search templates (mustache, parametrli saqlangan so'rov: SQL dagi saqlangan so'rov ekvivalenti), `_msearch`, `_validate/query?explain`
11. **Relevance va ranking**: TF-IDF tarixi va BM25 formulasi (`k1`, `b`, IDF, term frequency saturation, field length normalization), shard darajasidagi IDF muammosi va `dfs_query_then_fetch`, `explain: true` va `_explain` API ni o'qish, field boosting (`title^3`), `similarity` sozlash, relevance tuning metodologiyasi (judgement list, `_rank_eval` API: precision, recall, MRR, DCG/nDCG), business signal'larni aralashtirish (popularity, yangilik, stock), `rescore` (`window_size`, qimmat modelni faqat top-N ga), Learning to Rank qisqa (8.x da), hybrid search (BM25 + vector, RRF) 23-mavzuga ko'prik
12. **Sorting, pagination va katta natijalar**: `sort` (maydon, `_score`, ko'p darajali, `missing`, `mode` array uchun, `unmapped_type`), `text` ustida sort qilib bo'lmasligi va `keyword` sub-field, `from`+`size` deep pagination muammosi (`index.max_result_window` 10000, nega har shard `from+size` qaytaradi), `search_after` + tie-breaker, Point in Time (PIT, `_pit`, `keep_alive`, barqaror snapshot), `scroll` API va nega eskirgan (PIT + `search_after` tavsiya), `collapse` (field bo'yicha guruhlash, har mahsulotdan bitta variant), `sliced` scroll/PIT parallel eksport uchun, keyset pagination SQL dagi bilan solishtirish, frontend infinite scroll uchun to'g'ri dizayn

## IV bosqich: Aggregatsiya va so'rov tillari

13. **Aggregatsiyalar chuqur**: metric (`avg`, `sum`, `min`/`max`, `stats`/`extended_stats`, `value_count`, `cardinality` (HyperLogLog++, `precision_threshold`, nega taxminiy), `percentiles` (TDigest), `top_hits`, `top_metrics`), bucket (`terms` va nega taxminiy: `shard_size`, `doc_count_error_upper_bound`, `date_histogram` (`calendar_interval` vs `fixed_interval`, time zone), `histogram`, `range`/`date_range`, `filter`/`filters`, `nested`/`reverse_nested`, `significant_terms`, `geohash_grid`), `composite` (barcha bucketlarni sahifalab olish, `after_key`), pipeline (`derivative`, `cumulative_sum`, `moving_fn`, `bucket_script`, `bucket_selector` = SQL `HAVING`, `bucket_sort`), `size: 0` bilan faqat aggregatsiya, post_filter va fasetli qidiruv (tanlangan filtr boshqa fasetlarga ta'sir qilmasligi), `global` aggregatsiya, aggregatsiya xotirasi va `search.max_buckets`, SQL `GROUP BY` bilan har birini solishtirish
14. **ES|QL va SQL interfeysi**: ES|QL (8.11+, piped til: `FROM logs-* | WHERE status >= 500 | STATS count = COUNT(*) BY host | SORT count DESC | LIMIT 10`), buyruqlar (`FROM`, `WHERE`, `EVAL`, `STATS ... BY`, `KEEP`/`DROP`, `RENAME`, `DISSECT`/`GROK`, `ENRICH`, `MV_EXPAND`, `LOOKUP JOIN` yangi versiyalarda), `POST /_query` API, ES|QL vs Query DSL (qachon qaysi), Elasticsearch SQL (`POST /_sql?format=txt`, `translate` bilan DSL ga o'girish, cheklovlari: JOIN yo'q), EQL qisqa (hodisa ketma-ketligi, security uchun), Kibana Discover'da ES|QL, cheklovlar va versiyaga bog'liq xususiyatlarni hujjatdan tekshirish
15. **Vaqt qatorlari va log analytics**: `@timestamp`, ECS (Elastic Common Schema), data streams (append-only, backing indexlar `.ds-...`, `op_type: create`), TSDS (time series data stream, `index.mode: time_series`, dimension va metric maydonlar, downsampling), LogsDB index mode (8.17+, hajm tejash, versiyani tekshirish), `date_histogram` + `percentiles` dashboard so'rovlari, rollup/downsampling, ClickHouse va `timeseries/` moduli bilan solishtirish (qachon log uchun ES, qachon ClickHouse)

## V bosqich: Ma'lumot oqimi va scripting

16. **Ingest pipelines**: pipeline nima (indexlashdan oldin hujjatni o'zgartirish, Logstash'ning yengil alternativi), processorlar (`set`, `remove`, `rename`, `convert`, `date`, `grok`, `dissect`, `split`, `json`, `kv`, `lowercase`, `trim`, `gsub`, `geoip`, `user_agent`, `script`, `enrich`, `pipeline` (ichma-ich), `foreach`, `drop`, `fail`), `if` sharti (Painless), `on_failure` va xatoni alohida indexga yo'naltirish, `_simulate` API bilan test qilish (bu modulning unit testi), `default_pipeline`/`final_pipeline` index sozlamasida, enrich policy (lookup jadval bilan boyitish, SQL JOIN ekvivalenti), ingest node resurslari
17. **Painless scripting (procedura ekvivalenti)**: Painless sintaksisi (Java'ga o'xshash, tiplar, `def`, list/map, lambda), kontekstlar (`script_score`, `script_fields`, runtime field `emit`, `update` (`ctx._source`, `ctx.op = 'noop'/'delete'`), `_update_by_query`, `_delete_by_query`, `_reindex` script, ingest `script` processor, aggregatsiya scriptlari, `bucket_script`), `params` bilan parametrlash (nega literalni scriptga yozmaslik: kompilyatsiya keshi, `script.max_compilations_rate`), stored scripts (`PUT _scripts/name`: saqlangan procedura), `doc['field'].value` vs `params._source` (doc values tez, `_source` sekin), xavfsizlik (sandbox, allowlist), debug (`Debug.explain`), `_scripts/painless/_execute` bilan test, scriptlarning performance narxi va qachon mapping/ingest bilan almashtirish kerak
18. **Reindex, aliases va index templates**: `_reindex` (manba so'rov, `dest`, `op_type`, `conflicts: proceed`, remote reindex, `slices: auto`, `wait_for_completion=false` va `_tasks` API), `_update_by_query` mapping o'zgargandan keyin, aliases (`_aliases` atomar swap, zero-downtime reindex patterni: `products_v1` → `products_v2`, write alias `is_write_index`, filtered alias multi-tenant uchun), index templates (composable `_index_template` va `_component_template`, `priority`, `index_patterns`), legacy templates farqi, `_split`/`_shrink`/`_clone`, index `close`/`open`, mapping migratsiyasini versiyalash (ops/ dagi migratsiya mavzusi bilan bog'lash)

## VI bosqich: Ekspluatatsiya

19. **ILM, data tiers va rollover**: Index Lifecycle Management fazalari (`hot`, `warm`, `cold`, `frozen`, `delete`), harakatlar (`rollover` (`max_primary_shard_size`, `max_age`, `max_docs`), `shrink`, `forcemerge`, `allocate`, `searchable_snapshot`, `delete`), ILM policy yozish va `GET _ilm/explain`, data streams bilan ILM, data tiers (`data_hot`...) va node attributlari, data stream lifecycle (DSL, ILM ga soddaroq alternativa), retention siyosatini xarajat bilan bog'lash, lokal mashqda qisqa vaqt bilan (`indices.lifecycle.poll_interval`) ILM fazalar o'tishini kuzatish
20. **Performance va shard sizing**: shard o'lchami qoidalari (10–50 GB atrofida, har node heap GB ga shard soni tavsiyasi tarixi va hozirgi tavsiyalar), oversharding zarari, JVM heap (50% RAM, 31 GB compressed oops chegarasi, qolgani OS page cache uchun), indexlash tezligi (`_bulk` o'lchami 5–15 MB, parallel client, `refresh_interval: -1` va `number_of_replicas: 0` bulk yuklashda, keyin qaytarish, avtomatik `_id` tezroq), qidiruv tezligi (filter context va kesh, `request_cache`, `preference`, `index.sort` (index sorting va early termination), `eager_global_ordinals`, wildcard/regexp/leading wildcard narxi, `profile: true` bilan so'rov profilini o'qish), slow log (`index.search.slowlog.threshold`), hot threads (`_nodes/hot_threads`), thread pool rad etishlari (`_cat/thread_pool`, 429), circuit breakers, `esrally` benchmark qisqa
21. **Security**: 8.x default security (TLS, parol, enrollment token), built-in userlar (`elastic`, `kibana_system`), role va privilege (cluster, index, document level security, field level security), API keys (servislar uchun), service accounts, transport va HTTP TLS, audit log, IP filtering, xavfsiz konfiguratsiya (scriptlarni cheklash, `action.destructive_requires_name`), ES ni internetga ochiq qoldirishning real oqibatlari (ransomware tarixi), lokal konteynerda securityni yoqib qayta ulanish
22. **Snapshot, restore va cluster ekspluatatsiyasi**: snapshot repository (`fs`, `s3` (lokal `minio`), `path.repo`), snapshot inkremental tabiati (segment darajasida), `_snapshot` API (create, restore, `indices`, `rename_pattern`, partial), Snapshot Lifecycle Management (SLM), searchable snapshots (frozen tier), restore drill, rolling upgrade va rolling restart (`cluster.routing.allocation.enable: primaries`), cross-cluster replication va cross-cluster search qisqa, monitoring (Stack Monitoring, Metricbeat, `_cluster/stats`, `_nodes/stats`), keng tarqalgan nosozliklar: disk watermark (`low`/`high`/`flood_stage`, read-only index), unassigned shards, mapping explosion, GC pauzalari, OpenSearch farqlari (Security plugin, ISM vs ILM, OpenSearch Dashboards, k-NN plugin, PPL, API mosligi 7.10 dan ayrilish, AWS OpenSearch Service va Serverless)

## VII bosqich: Ekotizim va loyiha

23. **Vector va semantic search kirish**: `dense_vector` mapping (`dims`, `similarity`: `cosine`/`dot_product`/`l2_norm`, `index: true`), HNSW, `knn` qidiruv (`k`, `num_candidates`), quantization (`int8_hnsw`, `bbq` yangi versiyalarda, hujjatdan tekshirish), `sparse_vector` va ELSER (learned sparse retrieval), `semantic_text` va inference API, hybrid search (BM25 + kNN, RRF `retriever`), filtrlangan kNN, vector search chuqur `vector/` modulida, bu yerda faqat ES ichida qanday ishlashi va BM25 bilan birlashtirish
24. **Loyiha: e-commerce qidiruvi va observability**: (a) mahsulot qidiruvi: Postgres'dagi katalogdan Elasticsearch'ga sinxronlash (bulk boshlang'ich yuklash + outbox/CDC orqali inkremental), explicit mapping va o'zbek/rus analyzer, autocomplete (`search_as_you_type`), typo tolerance, fasetli navigatsiya (`post_filter` + aggregatsiyalar), `function_score` bilan popularity va stock, alias orqali zero-downtime reindex, `_rank_eval` bilan relevance o'lchovi; (b) ELK: Filebeat/Elastic Agent yoki ingest pipeline bilan konteyner loglarini data stream'ga, ILM, Kibana dashboard va ES|QL so'rovlar; `test.sh` bilan natijalar avtomatik tekshiriladi, README'da arxitektura va trade-off'lar
