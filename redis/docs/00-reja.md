# Redis rejasi: in-memory data structures, Lua va Functions, persistence, cluster va patternlar

Nima uchun alohida va muhim: Redis deyarli har bir backend tizimda bor: kesh, session store, rate limiter, queue, leaderboard, distributed lock, pub/sub, real-time hisoblagich. U "kesh" emas, xotiradagi data structure server: har bir strukturaning o'z murakkablik kafolati va ichki encoding'i bor, va noto'g'ri tanlangan struktura yoki `KEYS *` kabi bitta buyruq butun servisni to'xtatadi. Redis 8 bilan avval modul bo'lgan Query Engine, JSON, TimeSeries va probabilistic strukturalar asosiy distributivga kirdi, shuning uchun Redis endi document va search DB vazifalarini ham bajaradi. Bu reja ichki tuzilishdan (event loop, encoding, expiry) boshlab, har bir strukturani, server tomonidagi dasturlashni (MULTI/EXEC, Lua, Functions), persistence, replikatsiya, Cluster va production patternlarini chuqur o'rgatadi.

Boshlash: `theory/` dagi xotira va disk (latency raqamlari), replication va partitioning (hash slot = consistent hashing'ning boshqa ko'rinishi) mavzulari tavsiya etiladi. Asosiy SQL shart emas, Redis modulini parallel boshlash mumkin. Lua'ni bilmasangiz ham bo'ladi: V bosqichda kerakli qismi (o'zgaruvchi, jadval, `if`/`for`, funksiya) o'rgatiladi, JS bilimingiz yetarli asos.

Ishlash tartibi: `redis/docs/NN-nom.md` nazariya va vazifalar, kod `redis/NN-slug/main.redis` (har qatorda bitta redis-cli buyrug'i, `#` komment; `redis-cli < main.redis` bilan ishga tushadi), Lua skriptlar `*.lua` (`redis-cli --eval script.lua key1 , arg1`), Functions kutubxonalari `lib.lua` (`FUNCTION LOAD REPLACE`), tekshiruv `test.sh` (natijani kutilgan qiymat bilan solishtiradi). Pattern va benchmark vazifalarida (pipelining, lock, rate limiter) kichik Node.js (`node-redis`/`ioredis`), Go (`go-redis`) yoki Python (`redis-py`) skript, siz tanlaysiz.

```
make up db=redis              # ldb-redis (Redis 8, bitta instance)
make up db=redis-cluster      # 6 node'li Redis Cluster (3 master + 3 replica), VI bosqichdan
make up db=redis-sentinel     # master + 2 replica + 3 sentinel, VI bosqichda
make shell db=redis           # interaktiv redis-cli
make rds n=05                 # redis/05-*/main.redis
make rds-test n=05            # redis/05-*/test.sh
make reset db=redis
make check
```

## Boshqa DBlar bilan solishtirish

| Mavzu | PostgreSQL / relational | Redis | MongoDB | Memcached / Valkey |
|---|---|---|---|---|
| Saqlash joyi | disk + buffer pool | xotira, disk faqat persistence uchun | disk + WiredTiger cache | Memcached: faqat xotira; Valkey: Redis bilan bir xil |
| Model | jadval | kalit → data structure (string, list, hash, set, zset, stream, JSON) | hujjat | Memcached: kalit → blob |
| So'rov | SQL | buyruqlar (har strukturaga o'ziniki), Redis 8 da `FT.SEARCH` | MQL | `get`/`set` |
| Tranzaksiya | ACID, izolyatsiya darajalari | `MULTI`/`EXEC` (rollback yo'q), `WATCH`, Lua/Functions atomar | multi-document ACID | yo'q (`cas` bor) |
| Procedura | PL/pgSQL | Lua (`EVAL`), Redis Functions (`FCALL`) | `$function`, aggregation | yo'q |
| Trigger / hodisa | trigger, `LISTEN/NOTIFY` | keyspace notifications, Pub/Sub, Streams | change streams | yo'q |
| Durability | WAL, `fsync` | RDB snapshot, AOF (`appendfsync`), yo'qotish oynasi bor | journal | yo'q |
| Masshtablash | read replica, sharding qo'lda | replica, Sentinel, Cluster (16384 slot) | sharding | client-side hashing |
| Latency | ms | sub-ms | ms | sub-ms |

## I bosqich: Arxitektura va asoslar
1. **Redis nima va arxitekturasi**: in-memory data structure server, tarix (Salvatore Sanfilippo, 2009), single-threaded buyruq bajarish va event loop (`ae`, epoll/kqueue), nima uchun bitta thread tez (lock yo'q, CPU kesh, xotira tezligi; bottleneck odatda tarmoq), 6.0+ I/O threads (`io-threads`, faqat socket o'qish/yozish), background threadlar (`lazyfree`, AOF fsync, `UNLINK`), har buyruq atomar, sekin buyruq butun serverni bloklashi (`KEYS *`, katta `SMEMBERS`, `FLUSHALL` sinxron), RESP2 va RESP3 protokoli, `redis-benchmark`, litsenziya tarixi (BSD → 2024 da RSALv2/SSPLv1 → Redis 8 da AGPLv3 varianti qo'shilishi), Valkey fork (Linux Foundation, BSD), Redis Open Source vs Redis Software vs Redis Cloud
2. **redis-cli, keyspace va kalit dizayni**: `redis-cli` (`-h`, `-p`, `-n`, `--raw`, `--no-raw`, `-x`, `--pipe`, `--scan --pattern`, `--bigkeys`, `--memkeys`, `--latency`, `--stat`, `MONITOR` va uning narxi), database'lar (`SELECT 0–15`, Cluster'da faqat 0, nima uchun ko'p DB o'rniga prefiks), kalit nomlash konventsiyasi (`user:1001:profile`, `:` ajratgich), `EXISTS`, `DEL` vs `UNLINK`, `TYPE`, `OBJECT ENCODING`, `RENAME`, `COPY`, `KEYS` vs `SCAN` (cursor, `MATCH`, `COUNT`, `TYPE`, kafolatlar: dublikat bo'lishi mumkin), `DUMP`/`RESTORE`, `INFO` bo'limlari (`server`, `memory`, `stats`, `keyspace`, `persistence`, `replication`), `CONFIG GET/SET`, `redis.conf`
3. **TTL, expiry va eviction**: `EXPIRE`, `PEXPIRE`, `EXPIREAT`, `EXPIRETIME`, `TTL`, `PERSIST`, `SET ... EX/PX/EXAT/KEEPTTL`, 7.0+ `NX`/`XX`/`GT`/`LT` opsiyalari, kalit qayta yozilganda TTL yo'qolishi tuzog'i, expiry algoritmi: lazy (o'qishda) va active (har 100 ms tasodifiy namuna, `hz`, `active-expire-effort`), replica'da expiry (master `DEL` yuboradi), `maxmemory` va eviction policies (`noeviction`, `allkeys-lru`, `volatile-lru`, `allkeys-lfu`, `volatile-lfu`, `allkeys-random`, `volatile-random`, `volatile-ttl`), taxminiy LRU (namuna, `maxmemory-samples`), LFU hisoblagichi (`lfu-log-factor`, `lfu-decay-time`, `OBJECT FREQ`), kesh va DB sifatida ishlatishda qaysi siyosat, cache stampede va TTL'ga jitter qo'shish

## II bosqich: Data structures
4. **String, bitmap va bitfield**: string = binary-safe bayt massivi (512 MB gacha), ichki encoding'lar (`int`, `embstr` 44 baytgacha, `raw`, SDS), `SET` opsiyalari (`NX`, `XX`, `GET`), `GET`, `MGET`/`MSET`, `GETEX`, `GETDEL`, `INCR`/`INCRBY`/`INCRBYFLOAT`/`DECR` (atomar hisoblagich), `APPEND`, `GETRANGE`/`SETRANGE`, `STRLEN`, `LCS`, bitmap (`SETBIT`, `GETBIT`, `BITCOUNT`, `BITPOS`, `BITOP`: kunlik faol foydalanuvchi, feature flag), `BITFIELD` (bir nechta kichik hisoblagich bitta kalitda, `OVERFLOW WRAP/SAT/FAIL`), JSON'ni string sifatida saqlash vs Hash vs Redis JSON
5. **List**: ichki tuzilish (quicklist: listpack tugunlaridan iborat ikki tomonlama ro'yxat, `list-max-listpack-size`, `list-compress-depth`), `LPUSH`/`RPUSH`, `LPOP`/`RPOP` (count bilan), `LRANGE`, `LINDEX` (O(n)), `LINSERT`, `LSET`, `LREM`, `LTRIM` (capped list: oxirgi N ta hodisa), `LLEN`, `LPOS`, `LMOVE`/`BLMOVE` (ishonchli queue patterni), blocking amallar (`BLPOP`, `BRPOP`, `BLMPOP`, timeout), oddiy queue va uning muammolari (ack yo'q, xabar yo'qolishi), qachon List o'rniga Streams
6. **Hash**: ichki encoding (`listpack` kichik hash uchun, `hashtable` katta uchun, `hash-max-listpack-entries`/`-value` va xotira tejash), `HSET`/`HGET`/`HMGET`, `HGETALL` va katta hash'da xavfi, `HINCRBY`/`HINCRBYFLOAT`, `HSETNX`, `HDEL`, `HEXISTS`, `HKEYS`/`HVALS`/`HLEN`, `HSCAN`, `HRANDFIELD`, obyekt saqlash (user profili) va qisman yangilash, hash-field expiration (7.4+: `HEXPIRE`, `HPEXPIRE`, `HTTL`, `HPERSIST`; 8.0: `HGETEX`, `HSETEX`, `HGETDEL`), ko'p kichik kalit vs bitta katta hash (Instagram'ning xotira tejash misoli)
7. **Set**: encoding'lar (`intset`, `listpack` 7.2+, `hashtable`), `SADD`, `SREM`, `SISMEMBER`/`SMISMEMBER`, `SMEMBERS` vs `SSCAN`, `SCARD`, `SPOP`/`SRANDMEMBER` (tasodifiy tanlash, lotereya), set amallari (`SINTER`, `SUNION`, `SDIFF`, `*STORE` variantlari, `SINTERCARD` `LIMIT` bilan), murakkablik va katta set'lar kesishmasi narxi, patternlar: teglar, unikal tashrifchilar (aniq) va HyperLogLog bilan solishtirish, do'stlar kesishmasi
8. **Sorted Set**: ichki tuzilish (kichik: listpack, katta: skiplist + hashtable, nima uchun skiplist va balanced tree emas), `ZADD` (`NX`/`XX`/`GT`/`LT`/`CH`/`INCR`), `ZINCRBY`, `ZSCORE`/`ZMSCORE`, `ZRANK`/`ZREVRANK` (`WITHSCORE` 7.2+), `ZRANGE` (6.2+ yagona buyruq: `BYSCORE`, `BYLEX`, `REV`, `LIMIT`), `ZRANGESTORE`, `ZREM`, `ZREMRANGEBYSCORE`/`BYRANK`, `ZCOUNT`, `ZPOPMIN`/`ZPOPMAX`, `BZPOPMIN`, `ZUNIONSTORE`/`ZINTERSTORE` (`WEIGHTS`, `AGGREGATE`), `ZRANDMEMBER`, lexicographic range bilan autocomplete, patternlar: leaderboard, priority queue, delayed job queue (score = vaqt), sliding window rate limiter, vaqt bo'yicha indeks
9. **HyperLogLog va Geo**: HyperLogLog (12 KB da milliardlab elementni ±0.81% xato bilan sanash, `PFADD`, `PFCOUNT` bir nechta kalit bilan, `PFMERGE`, sparse va dense ko'rinish, algoritm intuitsiyasi: eng uzun nol prefiksi), qachon aniq Set va qachon HLL, Geo (sorted set ustida geohash, `GEOADD`, `GEOPOS`, `GEODIST`, `GEOSEARCH` `FROMMEMBER`/`FROMLONLAT` va `BYRADIUS`/`BYBOX`, `GEOSEARCHSTORE`, eskirgan `GEORADIUS`), "yaqin atrofdagi haydovchilar" patterni, aniqlik chegarasi, PostGIS bilan solishtirish
10. **Streams**: append-only log tuzilishi (radix tree + listpack), entry ID (`ms-seq`, `*` avtomatik), `XADD` (`MAXLEN ~`, `MINID` bilan trimming), `XLEN`, `XRANGE`/`XREVRANGE`, `XREAD` (`BLOCK`, `$`), `XTRIM`, `XDEL`, consumer groups (`XGROUP CREATE ... MKSTREAM`, `$` vs `0`), `XREADGROUP` (`>` yangi xabarlar va `0` o'z pending'lari), `XACK`, Pending Entries List (PEL), `XPENDING` (qisqa va kengaytirilgan shakl, idle time), `XCLAIM` va `XAUTOCLAIM` (o'lgan consumer xabarlarini olish), delivery count va dead letter patterni, `XINFO STREAM/GROUPS/CONSUMERS`, at-least-once va idempotent consumer, Kafka bilan solishtirish (partition yo'q, retention xotirada, `data-engineering/` havola)
11. **Kalit va xotira dizayni amaliyoti**: struktura tanlash qaror daraxti (qaysi so'rov: nuqtali o'qish, range, a'zolik, tartib, hisoblash), murakkablik jadvali (O(1), O(log n), O(n) buyruqlar va "katta n"), big key va hot key muammolari, katta kalitni bo'lish (sharding by suffix), `MEMORY USAGE`, `OBJECT ENCODING` bilan encoding o'zgarishini kuzatish, kichik struktura optimizatsiyasi (listpack chegaralari), seriyalash formati (JSON, MessagePack, protobuf), kalit prefiksi va namespace, `redis-cli --bigkeys`/`--memkeys`/`--hotkeys`

## V bosqich: Atomarlik va server-side dasturlash
17. **Pipelining va atomarlik modeli**: round-trip time (RTT) muammosi, pipelining (bir nechta buyruqni javob kutmasdan yuborish, `redis-cli --pipe` bilan bulk import, mass insertion protokoli), pipelining atomar emasligi, har bitta buyruq atomarligi va ko'p kalitli buyruqlar (`MSET`, `SMOVE`, `LMOVE`), "o'qib-hisoblab-yoz" race condition misoli (ikki client bir hisoblagichni `GET` + `SET` bilan oshiradi), uni hal qilishning to'rt yo'li: atomar buyruq (`INCR`), `MULTI`/`EXEC` + `WATCH`, Lua, Functions, benchmark: pipeline'siz vs pipeline bilan vs `MULTI` bilan
18. **Transactions: MULTI/EXEC va WATCH**: `MULTI`, buyruqlarni navbatga qo'yish (`QUEUED`), `EXEC`, `DISCARD`, kafolatlar: izolyatsiya (boshqa client buyrug'i orada bajarilmaydi) va "hammasi yoki hech biri bajariladi", lekin rollback yo'q (runtime xato bo'lsa qolganlari baribir bajariladi, masalan noto'g'ri tipdagi kalitga `INCR`), navbatga qo'yishda sintaksis xatosi butun tranzaksiyani bekor qilishi, `EXEC` ichida o'qilgan qiymatdan foydalanib bo'lmasligi, `WATCH` (optimistic locking, check-and-set, kalit o'zgarsa `EXEC` `nil` qaytaradi va client qayta urinadi), `UNWATCH`, retry loop'ini driverda yozish, relational ACID bilan solishtirish (durability AOF siyosatiga bog'liq), Cluster'da faqat bitta slot'dagi kalitlar
19. **Lua scripting**: Lua tezkor kirish (o'zgaruvchi, `local`, jadval, `#`, `ipairs`, `tonumber`/`tostring`, `if`, `for`, funksiya), `EVAL script numkeys key... arg...`, `KEYS` va `ARGV` jadvallari va nima uchun barcha kalitlar `KEYS` orqali berilishi shart (Cluster slot tekshiruvi, Functions'ga tayyorgarlik), `redis.call` (xato skriptni to'xtatadi) vs `redis.pcall` (xatoni qaytaradi), tip konvertatsiyasi (Lua table ↔ RESP array, `nil` va `false` tuzog'i, float'lar butun songa kesilishi), `redis.error_reply`/`redis.status_reply`, `redis.log`, `SCRIPT LOAD` + `EVALSHA` (`NOSCRIPT` xatosi va fallback), `SCRIPT EXISTS`/`FLUSH`/`KILL`, `EVAL_RO`/`EVALSHA_RO`, atomarlik (skript bajarilayotganda hech narsa bajarilmaydi), `busy-reply-threshold` (eski `lua-time-limit`) va sekin skript xavfi, deterministik bo'lmagan buyruqlar va effects replication (5.0+ default, 7.0 da yagona rejim), `redis-cli --eval`, `--ldb` Lua debugger, real misollar: atomar "o'qi va o'chir", rate limiter, lock'ni xavfsiz bo'shatish, inventarni kamaytirish shart bilan
20. **Redis Functions**: nima uchun Functions (7.0+): skriptlar serverda saqlanadi, nom bilan chaqiriladi, AOF/RDB va replikatsiya orqali persist qilinadi, `EVALSHA` cache muammosi yo'q, kutubxona tushunchasi (`#!lua name=mylib`, `redis.register_function`, `function_name` va `callback`, `flags`: `no-writes`, `allow-oom`, `allow-stale`, `no-cluster`), `FUNCTION LOAD` (`REPLACE`), `FCALL` va `FCALL_RO`, `FUNCTION LIST` (`WITHCODE`), `FUNCTION DELETE`, `FUNCTION FLUSH`, `FUNCTION DUMP`/`RESTORE` (deploy), `FUNCTION STATS`/`KILL`, kutubxona ichida umumiy yordamchi funksiyalar, versiyalash va deploy strategiyasi (CI dan `FUNCTION LOAD REPLACE`), Cluster'da har master'ga yuklash, stored procedure bilan solishtirish (PL/pgSQL: tranzaksiya, izolyatsiya, til imkoniyatlari), Functions'da biznes logika qancha bo'lishi kerak

## VI bosqich: Persistence, replikatsiya va Cluster
21. **Persistence: RDB va AOF**: RDB snapshot (`SAVE` vs `BGSAVE`, `fork()` va copy-on-write xotira narxi, `save 3600 1 300 100 60 10000` qoidalari, `dump.rdb`, `LASTSAVE`), AOF (append-only file, `appendonly yes`, `appendfsync always/everysec/no` va har birida yo'qotish oynasi, 7.0+ multi-part AOF: base + incremental fayllar va manifest, `BGREWRITEAOF`, `auto-aof-rewrite-percentage`), hybrid (`aof-use-rdb-preamble`), restart paytida tiklash tartibi, buzilgan AOF va `redis-check-aof`, persistence'siz kesh rejimi, `fork` uchun Linux'da `vm.overcommit_memory = 1` va transparent huge pages muammosi, durability va relational WAL bilan solishtirish

23. **Redis Cluster**: 16384 hash slot (`CRC16(key) mod 16384`), hash tag (`{user:1}:cart` va `{user:1}:profile` bitta slot'da), ko'p kalitli buyruq va Lua/`MULTI` cheklovi (`CROSSSLOT` xatosi), `MOVED` va `ASK` redirect, cluster-aware client va slot xaritasi kesh'i, `CLUSTER INFO`/`NODES`/`SLOTS`/`SHARDS`/`KEYSLOT`/`COUNTKEYSINSLOT`, `redis-cli --cluster create/check/fix/reshard/rebalance/add-node/del-node`, gossip (cluster bus, 16379 port), failover (replica promotion, `cluster-node-timeout`), `cluster-require-full-coverage`, Cluster'da faqat DB 0, Pub/Sub va sharded Pub/Sub, resharding paytida ishlash, Cluster vs Sentinel vs client-side sharding qarori, `theory/` dagi partitioning bilan bog'lash
24. **Xavfsizlik, latency va xotira diagnostikasi**: xavfsizlik: `protected-mode`, `bind`, `requirepass`, ACL (6.0+: `ACL SETUSER` `on`/`off`, `>password`, `~pattern` kalitlar, `%R~`/`%W~` 7.0+, `&channel`, `+@category`/`-command`, `ACL LIST`, `ACL WHOAMI`, `ACL LOG`, `ACL DRYRUN`, `aclfile`), `rename-command` (eskirgan, ACL afzal), TLS (`tls-port`), ochiq Redis'ga hujumlar tarixi (`CONFIG SET dir` bilan SSH kalit yozish), Lua sandbox; diagnostika: `SLOWLOG GET/LEN/RESET` (`slowlog-log-slower-than`), `LATENCY DOCTOR`/`HISTORY`/`LATEST` (`latency-monitor-threshold`), `redis-cli --latency`/`--latency-history`/`--intrinsic-latency`, `MEMORY DOCTOR`/`STATS`/`USAGE`/`MALLOC-STATS`, fragmentation (`mem_fragmentation_ratio`, `activedefrag`), `CLIENT LIST`/`KILL`/`NO-EVICT`, output buffer limitlari, `INFO commandstats` va `latencystats`, Prometheus `redis_exporter`

## VII bosqich: Patternlar va production
25. **Kesh patternlari**: cache-aside (lazy loading), read-through, write-through, write-behind (write-back) va har birining konsistentlik va xavfi, TTL strategiyasi va jitter, cache stampede (dogpile) va uning yechimlari: mutex/lock bilan qayta hisoblash, probabilistic early expiration (XFetch), stale-while-revalidate, negative caching, kesh invalidatsiyasi (o'chirish vs yangilash, DB tranzaksiyasidan keyin, CDC orqali), kesh kalitini versiyalash, HTTP kesh va CDN bilan qatlamlar (frontend tajribangiz bilan bog'lang), keshning hit ratio'sini o'lchash (`keyspace_hits`/`keyspace_misses`)
26. **Distributed lock, rate limiter va boshqa patternlar**: oddiy lock (`SET key token NX PX 30000`, bo'shatish faqat o'z token'i bilan Lua orqali), lock muddati va GC pause muammosi, Redlock algoritmi va Martin Kleppmann'ning tanqidi ("How to do distributed locking", fencing token yo'qligi) hamda Antirez javobi, qachon Redis lock yetarli (efficiency) va qachon emas (correctness: etcd/ZooKeeper yoki DB), rate limiter'lar: fixed window (`INCR` + `EXPIRE`), sliding window log (sorted set), sliding window counter, token bucket (Lua bilan), GCRA (`redis-cell` g'oyasi), leaderboard (sorted set, sahifalash, do'stlar orasida), session store (hash + TTL), idempotency key (`SET NX` + natijani saqlash), unikal ID generatori, delayed job queue va ishonchli queue (`LMOVE` yoki Streams), BullMQ/Sidekiq/Celery Redis'dan qanday foydalanishi, feature flag va bitmap
27. **Ekotizim va managed xizmatlar**: Valkey (Redis 7.2.4 fork'i, Linux Foundation, 8.x da ko'p-thread'li I/O yaxshilanishlari), KeyDB (multi-threaded fork), Dragonfly (Redis-mos, shared-nothing ko'p-thread'li arxitektura), Garnet (Microsoft), Memcached bilan solishtirish, managed: AWS ElastiCache (Redis OSS va Valkey), MemoryDB (durable, multi-AZ transaction log), Azure Cache for Redis / Azure Managed Redis, Google Memorystore, Redis Cloud, Upstash (serverless, HTTP API), docker'da Valkey'ni ishga tushirib bir xil skriptlarni sinash, driverlar (`node-redis`, `ioredis`, `go-redis`, `redis-py` va async, Lettuce/Jedis): connection pool, pipelining va cluster rejimi
28. **Kubernetes va production checklist**: production sozlamalari (`maxmemory` va eviction, persistence tanlash, `tcp-keepalive`, `timeout`, `vm.overcommit_memory`, THP o'chirish, `somaxconn`), xotira rejalash (dataset × fragmentation × fork uchun zaxira), monitoring metrikalari (used_memory, evicted_keys, connected_clients, blocked_clients, instantaneous_ops_per_sec, replication lag, rdb/aof holati), alerting, upgrade (replica'dan boshlab), backup (RDB faylini nusxalash va tiklashni sinash), Kubernetes'da Redis (StatefulSet, operatorlar, Helm chart'lar, Cluster rejimi va pod IP muammosi), anti-patternlar ro'yxati (`KEYS`, katta kalitlar, Redis'ni yagona haqiqat manbai sifatida durability'siz ishlatish, Pub/Sub'ni queue sifatida, har request'da yangi connection)
