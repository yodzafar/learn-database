# App rejasi: ilovadan ma'lumotlar bazasi bilan ishlash (Go, Python, TypeScript)

Nima uchun alohida: bazaning o'zini yaxshi bilish yetarli emas, ko'p muammo ilova va baza chegarasida tug'iladi: noto'g'ri sozlangan connection pool, har so'rovda yangi ulanish, ORM yaratgan N+1, tranzaksiya ichida HTTP chaqiruv, serialization failure'ni qayta urinmaslik, `OFFSET 100000` li pagination, "faqat bitta qator" deb yozilgan race condition, cache va baza o'rtasidagi nomuvofiqlik, Kafka'ga yuborib bazaga yozolmaslik (dual write). Bu modul bazaga ilova tomonidan qaraydi, lekin DB tomonidan o'lchaydi: har vazifada ilova nima yuborayotgani (`pg_stat_statements`, query log, `EXPLAIN`) ko'rib turiladi.

Til tanlovi: har vazifa Go, Python yoki TypeScript (Node) dan birida bajariladi, foydalanuvchi tanlaydi (tavsiya: TS siz uchun eng tez, Go va Python parallel o'qilayotgan loyihalarni mustahkamlaydi; muhim mavzularni ikki tilda qilish foydali). Til chuqurligi o'z loyihalarida: Python'da SQLAlchemy va Alembic chuqur ../learn-python (28-dars), Go'da `database/sql` va `pgx` ../learn-golang; bu yerda cross-language va DB nuqtai nazaridan: bir xil tushuncha uch ekotizimda qanday ko'rinadi va baza unga qanday reaksiya qiladi.

Boshlash: `sql/` I–III bosqich, `theory/` dagi tranzaksiya va isolation mavzulari, `postgres/` I–III bosqich (asosiy mashqlar Postgres'da, keyin MySQL, MongoDB, Redis, Cassandra). Tanlangan tilda asoslar va HTTP servis yozish (Go: learn-golang IV bosqich, Python: learn-python IV bosqich, TS: Node/Express yoki Fastify tajribasi).

Ishlash tartibi: `app/docs/NN-nom.md` nazariya va vazifalar, kod `app/NN-slug/<til>/` da: `go/` (`main.go`, `main_test.go`, `go.mod`), `python/` (`main.py`, `test_main.py`, `uv` loyiha), `ts/` (`main.ts`, `main.test.ts`, `package.json`, `vitest`), umumiy sxema `app/NN-slug/schema.sql` va kerak bo'lsa `compose.yaml`. Testlar haqiqiy bazaga qarshi (testcontainers yoki `make up` dagi konteyner), mock bazaga emas. Buyruqlar: `make app n=01` (til `lang=go|python|ts`, default `.app-lang` faylidan), `make app-test n=01 lang=go`, `make run d=app/05-pagination/ts`, `make check` (tanlangan til lint/type-check: `go vet` + `golangci-lint`, `ruff` + `mypy --strict`, `tsc --noEmit` + `eslint`). Har vazifada DB tomoni ham tekshiriladi: `make shell db=postgres` va `pg_stat_statements` dan ilova yuborgan so'rovlarni ko'rish.

## I bosqich: Ulanish va so'rov

1. **Driver va wire protokollari**: driver nima qiladi (ulanish, autentifikatsiya, so'rov yuborish, natijani tiplarga o'girish), protokollar qisqa ko'rinishda: PostgreSQL frontend/backend protokoli (simple query vs extended query: `Parse`/`Bind`/`Execute`/`Sync`, text vs binary format, `COPY` sub-protokoli, `NOTIFY`), MySQL client/server protokoli (`COM_QUERY` vs `COM_STMT_PREPARE`/`COM_STMT_EXECUTE`), SQL Server TDS, Oracle TNS/Net8 (va thin driverlar: `python-oracledb` thin, `node-oracledb` thin), TLS va `sslmode` ilovada, connection string formatlari (URI vs key=value, multi-host), Wireshark yoki `pgbadger`/`log_statement=all` bilan ilova nima yuborayotganini ko'rish, tip xaritasi (`numeric` → Go `pgtype.Numeric`/Python `Decimal`/JS `string`, `bigint` JS da `number` emas, `timestamptz` va time zone, `NULL` → `sql.NullString`/`None`/`null`), vazifa: bitta so'rovni uch tilda yuborib protokol darajasidagi farqni log orqali ko'rish
2. **Connection pool**: nega pool (ulanish narxi: TCP + TLS + auth + backend process), pool parametrlari (`max_open`/`max_conns`, `min_idle`, `max_lifetime`, `max_idle_time`, `acquire_timeout`/`connectionTimeoutMillis`, health check), `database/sql` `SetMaxOpenConns`/`SetMaxIdleConns`/`SetConnMaxLifetime` va default'larning xavfi (cheksiz), `pgxpool` va `sql.DB` farqi, `psycopg_pool` va SQLAlchemy `QueuePool` (`pool_pre_ping`, `pool_recycle`), `pg.Pool` (`max`, `idleTimeoutMillis`), pool o'lchami formulasi (HikariCP tavsiyasi: `cores * 2 + effective_spindle_count` g'oyasi va nega kichik pool tezroq), ko'p instansiya × pool = baza `max_connections` hisobi, serverless (Lambda) va pool muammosi, PgBouncer transaction mode bilan ishlash (`ops/` 18-mavzu bilan bog'liq), pool exhaustion belgilari va sabablari (ulanishni qaytarmaslik, `rows.Close()` unutish, tranzaksiya ichida uzoq ish), vazifa: pool o'lchamini 1, 5, 20, 100 qilib yuklama (k6/`hey`) ostida latency va bazadagi `pg_stat_activity` holatini o'lchash
3. **Prepared statements, parametrizatsiya va SQL injection**: placeholder sintaksislari (`$1` PG, `?` MySQL/SQLite, `@p1` MSSQL, `:name` Oracle va SQLAlchemy), server-side vs client-side prepared statements (driver aslida nima qiladi: `pgx` avtomatik statement cache, `mysql2` `execute` vs `query`, `psycopg` `prepare_threshold`), prepared statement va PgBouncer transaction mode muammosi, SQL injection (klassik misollar, ORM'da ham bo'ladi: raw fragment, `ORDER BY` ustun nomi, `IN` ro'yxati, `LIKE` pattern, JSON yo'l), identifikatorlarni xavfsiz qo'shish (allowlist, `pgx.Identifier`, `psycopg.sql.Identifier`, `format('%I')`), template string kutubxonalari (`postgres` porsager tagged template, Prisma `$queryRaw` vs `$queryRawUnsafe`, Drizzle `sql` tag), second-order injection, vazifa: zaif endpoint yozib injection'ni isbotlash, so'ng uch xil usulda tuzatish
4. **Natijalarni o'qish va katta hajm**: row scanning (`rows.Scan`, `pgx.CollectRows` va `RowToStructByName`, `psycopg` row factory `dict_row`/`class_row`, JS'da obyekt qatorlar), streaming vs hammasini xotiraga (server-side cursor: `psycopg` named cursor, `pgx` rows iterator, `pg-cursor`/`pg-query-stream`, MySQL `useCursorFetch`), bulk insert usullari va tezligi (bitta-bitta `INSERT` vs multi-row `VALUES` vs `executemany`/batch vs `COPY FROM STDIN`: `pgx.CopyFrom`, `psycopg` `copy`, `pg-copy-streams`; MySQL `LOAD DATA LOCAL INFILE`), `pgx` batch (`SendBatch`, pipeline mode), `unnest` bilan array orqali bulk upsert, vazifa: 1 million qatorni har usulda yozib vaqt va baza yuklamasini jadvalda solishtirish

## II bosqich: Tranzaksiya va konkurentlik

5. **Tranzaksiyalarni ilovada boshqarish**: `BEGIN`/`COMMIT`/`ROLLBACK` driverlarda (`tx, err := pool.Begin(ctx)` va `defer tx.Rollback(ctx)` idiomasi, Python `with conn.transaction():`, SQLAlchemy `Session.begin()`, Prisma `$transaction` interactive va batch, Drizzle/Kysely `transaction()`), tranzaksiyani funksiyalar bo'ylab uzatish (context, unit of work, `withTx` helper), savepoint va ichma-ich tranzaksiya (`SAVEPOINT`, SQLAlchemy `begin_nested`), autocommit tuzog'i (Python DB-API default'lari, MySQL `autocommit`), tranzaksiya ichida tashqi chaqiruv (HTTP, queue) qilmaslik va uzun tranzaksiya zarari (lock, vacuum, pool), `idle in transaction` ni ilova xatosidan topish, isolation level'ni ilovadan belgilash (`pgx.TxOptions`, `SET TRANSACTION ISOLATION LEVEL`), read-only tranzaksiyalar, vazifa: pul o'tkazish servisi (ikki hisob), xato bo'lganda to'liq rollback isboti
6. **Konkurent yangilanishlar va locking**: lost update muammosi (read-modify-write), yechimlar jadvali: atomik `UPDATE ... SET balance = balance - $1 WHERE ... AND balance >= $1`, pessimistic locking (`SELECT ... FOR UPDATE`, `FOR UPDATE NOWAIT`, `SKIP LOCKED`, `FOR SHARE`), optimistic locking (`version` ustuni, `UPDATE ... WHERE id = $1 AND version = $2` va affected rows tekshiruvi, ORM'larda: GORM, SQLAlchemy `version_id_col`, TypeORM `@VersionColumn`), advisory lock (`pg_advisory_xact_lock`, MySQL `GET_LOCK`) qachon, `SKIP LOCKED` bilan ish navbati (job queue) yozish, deadlock (tartib bilan lock olish, aniqlash va qayta urinish), vazifa: 100 parallel so'rov bilan har usulni sinab, yo'qolgan yangilanishlarni sanash va qaysi biri to'g'ri ekanini isbotlash
7. **Serialization failure va retry**: `SERIALIZABLE` va `REPEATABLE READ` da xatolar (`40001` serialization_failure, `40P01` deadlock_detected, MySQL `1213` deadlock, `1205` lock wait timeout), qaysi xatolar retry qilinadi va qaysilari yo'q (SQLSTATE bo'yicha klassifikatsiya), retry loop to'g'ri yozish (butun tranzaksiyani qayta bajarish, exponential backoff + jitter, maksimal urinish, tranzaksiya ichida yon ta'sir bo'lmasligi), driverlarda xato kodini olish (`pgconn.PgError.Code`, `psycopg.errors.SerializationFailure`, `pg` `err.code`), CockroachDB/Spanner kabi bazalarda retry majburiyligi (`newsql/` bilan bog'liq), vazifa: `SERIALIZABLE` da write skew stsenariysi (navbatchi shifokorlar misoli) va retry bilan to'g'ri ishlashini isbotlash
8. **Idempotency va xatolarga chidamli yozish**: tarmoq xatosi bo'lganda "commit bo'ldimi yo'qmi" noaniqligi, idempotency key patterni (`idempotency_keys` jadvali, unique constraint, so'rov hash'i, javobni saqlash, Stripe uslubi), upsert (`INSERT ... ON CONFLICT DO UPDATE/NOTHING`, MySQL `ON DUPLICATE KEY UPDATE`, `MERGE`) va uning race'lardagi xatti-harakati, natural key vs surrogate key va dublikatlardan himoya, timeout'lar (statement_timeout ilovadan, context deadline Go'da, `AbortSignal` TS'da, driver va baza timeout'larining farqi, bekor qilingan so'rov bazada davom etishi), vazifa: to'lov endpoint'ini ikki marta yuborilganda bir marta bajarilishini isbotlash

## III bosqich: Ma'lumotga kirish qatlami

9. **Raw SQL vs query builder vs codegen vs ORM**: spektr va trade-off (nazorat, tip xavfsizligi, unumdorlik, migratsiya, o'rganish narxi, murakkab so'rovlar), Go: `sqlc` (SQL'dan tipli kod generatsiya, eng tavsiya etiladigan yo'l), `sqlx`, `squirrel`, GORM (qulay, lekin yashirin so'rovlar), ent (graph-uslubdagi schema-as-code); Python: SQLAlchemy Core vs ORM (Unit of Work, identity map), SQLModel; TS: Prisma (schema DSL, generated client, query engine tarixi va Rust'siz yangi arxitektura), Drizzle (SQL-like, yengil), Kysely (tipli query builder), TypeORM (Active Record/Data Mapper, decorator), Active Record vs Data Mapper patternlari, ORM'ning "leaky abstraction" joylari, vazifa: bitta murakkab so'rovni (window function + CTE) har yondashuvda yozib, generatsiya qilingan SQL va `EXPLAIN` ni solishtirish
10. **N+1 va so'rovlar sonini nazorat qilish**: N+1 qanday paydo bo'ladi (lazy loading, GraphQL resolver, sikl ichida so'rov), aniqlash (query log, `pg_stat_statements` calls soni, ORM logging, testda so'rovlar sonini assert qilish), eager loading strategiyalari (`JOIN` bilan: SQLAlchemy `joinedload`, Prisma `include`; alohida `IN` so'rov bilan: `selectinload`, GORM `Preload`, Drizzle relational queries), DataLoader patterni (batching, GraphQL uchun, Go `dataloaden`, JS `dataloader`), JSON aggregatsiya bilan bitta so'rovda ichma-ich javob (`json_agg`, `jsonb_build_object`: Postgres'dan API-ready JSON), cartesian explosion (ko'p `JOIN` + eager), vazifa: buyurtmalar va mahsulotlar ro'yxati endpointini N+1 dan 1–2 so'rovga tushirish, testda so'rovlar soni bilan isbot
11. **Pagination va qidiruv filtrlari**: `OFFSET`/`LIMIT` muammosi (chuqur sahifada sekinlik, sahifa siljishi yangi qator qo'shilganda), keyset (seek) pagination (`WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20`, row value comparison, mos composite index), cursor'ni kodlash (opaque base64, imzolash), ikki tomonga pagination, umumiy son (`COUNT(*)`) narxi va taxminiy son (`reltuples`), dinamik filtrlar va saralashni xavfsiz qurish (allowlist), full-text qidiruvni qachon `elasticsearch/` ga topshirish, GraphQL Relay connection spetsifikatsiyasi, vazifa: 10 million qatorli jadvalda offset va keyset'ni 1-, 100-, 10000-sahifada o'lchash
12. **Migratsiyalar ilova hayot siklida**: migratsiyani qachon ishga tushirish (ilova startida emas: race va huquq muammosi; alohida job, init container, CI bosqichi), ORM migratsiya generatorlari (Alembic autogenerate, Prisma Migrate, Drizzle Kit, GORM `AutoMigrate` va nega productionda xavfli) va ularning ko'r joylari (rename vs drop+add, index `CONCURRENTLY`, ma'lumot migratsiyasi), expand/contract ni ilova kodi bilan muvofiqlashtirish (N va N+1 versiya), feature flag bilan schema o'zgarishi, `ops/` 4–5 mavzulari bilan bog'liq, vazifa: ustunni qayta nomlashni ikki deploy davomida downtime'siz bajarish

## IV bosqich: Arxitektura patternlari

13. **Outbox pattern va dual write**: dual write muammosi (bazaga yozib Kafka'ga yuborolmaslik va aksincha), transactional outbox (biznes yozuvi va `outbox` qatori bitta tranzaksiyada), relay usullari (polling `SELECT ... FOR UPDATE SKIP LOCKED`, CDC: Debezium outbox event router, Postgres logical decoding), inbox pattern va consumer tomonida idempotency, tartib kafolati (aggregate bo'yicha), outbox jadvalini tozalash, `LISTEN`/`NOTIFY` bilan relay'ni uyg'otish, vazifa: buyurtma yaratish + "OrderCreated" hodisasini outbox orqali Redis Streams yoki Kafka'ga yetkazish, relay'ni o'ldirib ham hodisa yo'qolmasligini isbotlash
14. **CQRS va read replica routing**: o'qish va yozishni ajratish sabablari, read replica'ga yo'naltirish (ilovada ikki pool, Go'da resolver, SQLAlchemy binds/routing session, Prisma read replicas extension, ProxySQL/pgpool orqali), replication lag va read-your-writes (yozgandan keyin primary'dan o'qish, LSN/GTID kuzatish, "sticky" sessiya), CQRS (alohida read model, materialized view, denormalizatsiyalangan jadval, Elasticsearch read model), read model'ni yangilash (sinxron, outbox orqali asinxron), eventual consistency'ni UI'da ko'rsatish (frontend tajribangiz bilan bog'liq), vazifa: primary + replica bilan routing va lag ostida read-your-writes muammosini ko'rsatib tuzatish
15. **Kesh qatlami (Redis bilan)**: cache-aside, read-through, write-through, write-behind, kalit dizayni va versiyalash, TTL va jitter, invalidation strategiyalari (yozishda o'chirish, hodisa orqali, TTL), cache stampede (singleflight Go'da, lock bilan, probabilistic early expiration), cache va baza nomuvofiqligi (o'chirish va yozish tartibi, "delete after commit"), negative caching, serializatsiya va hajm, nimani keshlamaslik, `redis/` moduli bilan bog'liq, vazifa: mahsulot endpointiga cache-aside va stampede himoyasini qo'shib, yuklama ostida bazaga tushgan so'rovlar sonini o'lchash
16. **Multi-tenancy**: modellar va trade-off'lar (database-per-tenant, schema-per-tenant, shared table + `tenant_id`), shared modelda izolyatsiya (har so'rovda `tenant_id`, ORM global filtrlar, Postgres Row-Level Security: `CREATE POLICY`, `current_setting('app.tenant_id')`, `SET LOCAL` va pool bilan xavfli o'zaro ta'sir), schema-per-tenant'da `search_path` va migratsiya narxi, noisy neighbor, tenant'ni ko'chirish va o'chirish, sharding'ga o'sish (Citus `distribution column`), vazifa: shared modelda RLS bilan izolyatsiya va bitta tenant boshqasini ko'ra olmasligini testda isbotlash
17. **Soft delete, audit va event sourcing saqlash**: soft delete (`deleted_at`, partial unique index `WHERE deleted_at IS NULL`, ORM'larda default scope va uning tuzoqlari, GDPR bilan ziddiyat), audit trail (trigger asosida JSON diff jadvali, ilova asosida, temporal jadvallar: SQL:2011 system-versioned, MSSQL/MariaDB'da bor, Postgres'da `temporal_tables` extension yoki trigger), `created_by`/`updated_at` avtomatik, event sourcing'ni relational bazada saqlash (`events` jadvali: `stream_id`, `version`, unique `(stream_id, version)` optimistic concurrency, snapshot'lar, projection'lar), EventStoreDB/Marten g'oyasi qisqa, vazifa: hisob (account) aggregate'ini event sourcing bilan saqlash va projection'ni qayta qurish

## V bosqich: Sifat va boshqa DBlar

18. **Testlash**: haqiqiy bazaga qarshi test (mock emas) nega, testcontainers (Go, Python, TS), test izolyatsiyasi usullari (har test tranzaksiyada va oxirida rollback, har test uchun template database `CREATE DATABASE ... TEMPLATE`, truncate), fixtures va factory'lar, migratsiyalarni testda qo'llash, parallel testlar, so'rovlar sonini va sekin so'rovlarni testda assert qilish, contract test repository qatlami uchun, CI'da tezlik (konteyner qayta ishlatish, `tmpfs`, `fsync=off` faqat testda), vazifa: repository qatlami uchun to'liq test to'plami, CI'da 30 soniyadan kam
19. **Observability ilova tomondan**: OpenTelemetry DB instrumentatsiyasi (`otelpgx`/`otelsql` Go, `opentelemetry-instrumentation-psycopg`/`sqlalchemy` Python, `@opentelemetry/instrumentation-pg` TS), span atributlari (`db.system`, `db.query.text` va maxfiylik: literalni olib tashlash), trace'ni bazaga uzatish (`sqlcommenter`: so'rovga `/*traceparent=...*/` komment qo'shish va `pg_stat_statements`/log'da ko'rish), pool metrikalari (kutish vaqti, band ulanishlar), sekin so'rovlarni ilova logida, Jaeger/Tempo + Grafana lokal, vazifa: HTTP so'rovdan bazadagi so'rovgacha bitta trace ko'rsatish
20. **NoSQL driverlari bilan ishlash**: MongoDB (connection string va pool `maxPoolSize`, `readPreference`, `writeConcern`/`readConcern`, session va multi-document transaction, `retryWrites`, BSON tip xaritasi `ObjectId`/`Decimal128`, schema validation va Mongoose/ODM, aggregation pipeline'ni koddan qurish), Redis (pipelining, `MULTI`/`EXEC`, Lua script'ni `EVALSHA` bilan, connection pool, cluster client va hash tag, pub/sub ulanishi alohida), Cassandra (token-aware va DC-aware load balancing policy, prepared statements majburiy, consistency level per query, paging state, idempotent so'rovlar va speculative execution, retry policy, batch'ni noto'g'ri ishlatish), har driverda timeout va retry semantikasi, `mongodb/`, `redis/`, `cassandra/` modullari bilan bog'liq, vazifa: bir xil "foydalanuvchi profili" repository interfeysini uch NoSQL bazada yozish

## VI bosqich: Loyiha

21. **Loyiha: bitta servis, uch xil DB**: "buyurtmalar" servisi (REST yoki GraphQL) tanlangan tilda, repository interfeysi orqali uch backend: PostgreSQL (asosiy: tranzaksiyalar, keyset pagination, outbox, RLS multi-tenancy), MongoDB (hujjat modeli, multi-document transaction), Cassandra yoki DynamoDB Local (query-first model, eventual consistency) + Redis kesh; har backend uchun testcontainers testlar va bir xil contract test to'plami, k6 bilan yuklama testi va har backendda p50/p99 va bazaga tushgan so'rovlar soni, OpenTelemetry trace, README'da har model qaysi talabga mos va qaysida qiynaldi degan xulosa (ADR ko'rinishida), ixtiyoriy: ikkinchi tilda shu servisni qayta yozish
