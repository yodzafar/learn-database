# NewSQL rejasi: taqsimlangan SQL bazalar (Spanner, CockroachDB, YugabyteDB, TiDB)

Nima uchun alohida: klassik relyatsion bazalar (PostgreSQL, MySQL) bitta yozuvchi node'ga tayanadi; o'sish chegarasiga yetganda kompaniyalar qo'lda sharding (ilova darajasida) yoki NoSQL'ga (ACID va JOIN'dan voz kechib) o'tardi. NewSQL bu ikki dunyoni birlashtirishga urinish: SQL va ACID tranzaksiyalar saqlanadi, ma'lumot esa avtomatik bo'linib (range/tablet), Raft bilan replikatsiya qilinadi va node qo'shish orqali gorizontal kengayadi. Bu modul uch ochiq kodli implementatsiyani (CockroachDB: PostgreSQL wire protokoli, YugabyteDB: PostgreSQL kodi ustiga qurilgan, TiDB: MySQL mos) va ularning ilhom manbai Google Spanner'ni o'rganadi. Maqsad: qachon NewSQL haqiqatan kerak, qachon yaxshi sozlangan PostgreSQL yetadi, va taqsimlangan SQL'da sxema dizayni nega boshqacha ekanini isbot bilan bilish.

Boshlash: `theory/` dagi distributed bosqich (replication, partitioning, consensus/Raft, CAP/PACELC, distributed transactions va 2PC, clock'lar: Lamport, HLC) majburiy, chunki bu yerda nazariya takrorlanmaydi, faqat implementatsiya. `sql/` I–IV bosqich va `postgres/` I–III bosqich (TiDB uchun `mysql/` I–II) tanish bo'lishi kerak. `learn-golang/distributed` yoki `learn-python/distributed` dagi Raft laboratoriyasi qilingan bo'lsa, II bosqich ancha oson.

Ishlash tartibi: `newsql/docs/NN-nom.md` nazariya va vazifalar, kod `newsql/NN-slug/main.sql` (yoki `task_N.sql`) va `test.sql`, ba'zi vazifalarda klaster boshqaruvi uchun `cluster.sh` (node to'xtatish, tarmoqni uzish). Muhit: `make up db=cockroach` (bitta tugun `ldb-cockroach`; 3 tugunli klaster `ldb-cockroach-1..3` replikatsiya va chaos mavzularida `newsql/docker-compose.cluster.yml` bilan qo'shiladi), `make up db=yugabyte`, `make up db=tidb` (standalone; PD + TiKV + TiFlash to'liq klaster TiDB mavzusida alohida compose bilan), `make shell db=cockroach`, `make nsql n=03 db=cockroach` (`newsql/03-*/main.sql` ni tanlangan bazada ishga tushiradi, default `cockroach`), `make test d=newsql/03-...`, `make reset db=cockroach`, `make check`. Uch klasterni bir vaqtda ko'tarmang: Mac'da RAM yetmaydi, mavzuga kerakligini ishga tushiring.

## I bosqich: NewSQL g'oyasi va Spanner

1. **NewSQL nima va qayerdan kelgan**: monolit RDBMS ning o'sish chegarasi (vertikal scaling narxi, bitta writer), qo'lda sharding og'rig'i (cross-shard JOIN va tranzaksiya yo'q, resharding, ilova murakkabligi), NoSQL to'lqini va uning narxi (eventual consistency, JOIN yo'qligi), NewSQL ta'rifi (Pavlo va Aslett maqolasi), uch oila: yangi arxitektura (Spanner, CockroachDB, YugabyteDB, TiDB), middleware sharding (Vitess, Citus, ShardingSphere), cloud-native storage (Aurora, AlloyDB, Neon: compute/storage ajratish, lekin bitta writer), "distributed SQL" atamasi, OLTP vs HTAP, taqsimlangan SQL'ning asosiy narxi: har yozish konsensus raundi va tarmoq latency'si
2. **Google Spanner modeli**: Spanner maqolasi (2012) asosiy g'oyalari, TrueTime API (`TT.now()` interval qaytaradi: `[earliest, latest]`, epsilon), commit wait va external consistency (strict serializability) qanday kafolatlanadi, Paxos group, split va directory, read-write tranzaksiya (2PC + Paxos, lock'lar), read-only tranzaksiya (lock'siz, snapshot timestamp), stale read (bounded staleness), interleaved tables va parent-child lokalligi, F1 qatlami, Spanner'ning hozirgi holati (GoogleSQL va PostgreSQL interfeysi, Spanner emulator lokal mashq uchun), nega TrueTime'siz bazalar (CockroachDB, YugabyteDB) HLC va noaniqlik oynasi bilan ishlaydi
3. **Taqsimlangan SQL ning umumiy arxitekturasi**: qatlamlar: SQL layer (parser, optimizer, distributed execution) va transactional KV layer, sorted key-value map ga jadval va indeks qanday kodlanadi (`/table_id/index_id/pk` kalitlari), ma'lumotni bo'lish: range-based vs hash-based (avtomatik split va merge, rebalancing), har bo'lak Raft guruhi (leader/leaseholder, follower, quorum yozish), MVCC va timestamp ordering, distributed transaction protokollari (parallel commits, transaction record, write intents), clock skew muammosi va uncertainty interval, metadata (meta ranges, PD), lokal o'rganish uchun bu arxitekturani `theory/` dagi nazariya bilan bog'lash

## II bosqich: CockroachDB chuqur

4. **CockroachDB: o'rnatish va asoslar**: docker compose bilan 3 node'li insecure klaster (`cockroach start --join`, `cockroach init`), `cockroach sql`, DB Console (8080 port: ranges, replication, hot ranges, SQL activity), PostgreSQL bilan moslik va farqlar (`SERIAL` → `unique_rowid()`, `INT` = 64 bit, `STRING`, `JSONB`, `ARRAY`, inverted index, `UUID` va `gen_random_uuid()`), `SHOW RANGES FROM TABLE`, `SHOW CREATE`, `crdb_internal` va `system` sxemalari, psql va oddiy PostgreSQL driverlar bilan ulanish (pgx, psycopg), PL/pgSQL qo'llab-quvvatlash holati (user-defined functions, stored procedures, triggerlar keyingi versiyalarda qo'shilgan: aniq versiyani hujjatdan tekshirish vazifasi), qo'llab-quvvatlanmaydigan PostgreSQL xususiyatlari ro'yxati
5. **Ranges, replication va Raft amalda**: range nima, split (o'lcham va load bo'yicha), merge, replication factor (`ALTER RANGE default CONFIGURE ZONE USING num_replicas = 3`), leaseholder va Raft leader farqi (o'qish leaseholder'dan), lease transfer, under-replicated va unavailable ranges, node o'chirilganda nima bo'ladi (3 dan 1 tasi: ishlaydi, 3 dan 2 tasi: quorum yo'q), `cockroach node decommission`, rebalancing, zone config (`ALTER TABLE ... CONFIGURE ZONE`), replica'larni node'lar bo'yicha joylashtirish (localities, constraints), follower reads, DB Console'da replikatsiyani kuzatish
6. **Tranzaksiyalar: SERIALIZABLE, retry va 40001**: default `SERIALIZABLE` va nega CockroachDB uni tanladi, `READ COMMITTED` qo'llab-quvvatlash (yangi versiyalarda, cluster setting bilan), write intents, transaction record, parallel commits, read refresh, timestamp push, uncertainty restart (`ReadWithinUncertaintyIntervalError`), transaction contention, `40001` (`restart transaction`) xatosi va client-side retry (savepoint `cockroach_restart` protokoli, driver helper'lari: Go `crdbpgx.ExecuteTx`), retry'ni kamaytirish (qisqa tranzaksiyalar, `SELECT FOR UPDATE`, bitta statement'da yozish), `SHOW TRANSACTIONS`, contention'ni DB Console va `crdb_internal.transaction_contention_events` da ko'rish, idempotent retry dizayni
7. **Vaqt bo'yicha so'rov, CDC va bulk amallar**: `AS OF SYSTEM TIME` (`'-10s'`, `follower_read_timestamp()`), stale read va follower reads (latency va contention'ni kamaytirish), GC TTL (`gc.ttlseconds`) va uning chegarasi, changefeeds (CDC: `CREATE CHANGEFEED FOR TABLE ... INTO 'kafka://...'`, `webhook`, `resolved` timestamp, `updated`, `diff`, sinkless changefeed `EXPERIMENTAL CHANGEFEED FOR` lokal mashq uchun), `IMPORT INTO` va `COPY`, `EXPORT`, `BACKUP`/`RESTORE` (full va incremental, `AS OF SYSTEM TIME`), row-level TTL (`ttl_expire_after`), `data-engineering/` dagi CDC mavzusiga ko'prik
8. **Multi-region va survival goals**: regionlar va zonalar (`--locality=region=...,zone=...`), lokal docker'da simulyatsiya (har node'ga turli locality va `tc`/toxiproxy bilan latency), `ALTER DATABASE ... PRIMARY REGION`/`ADD REGION`, table locality: `REGIONAL BY TABLE`, `REGIONAL BY ROW` (`crdb_region` ustuni), `GLOBAL` (tez o'qish, sekin yozish: non-blocking transactions), survival goal: `ZONE` vs `REGION` failure (`SURVIVE REGION FAILURE`), latency budjeti va fizika (yorug'lik tezligi, region'lararo RTT), data domiciling (GDPR uchun ma'lumot hududi), multi-region'ning narxi (yozish latency, replika soni)
9. **CockroachDB'da optimizer va performance**: cost-based optimizer, `EXPLAIN`, `EXPLAIN ANALYZE (DISTSQL)` va distributed plan diagrammasi, DistSQL (so'rovni ma'lumot joylashgan node'larga yuborish), lookup join, merge join, hash join, zigzag join, vectorized execution engine, index turlari: secondary, `STORING` (covering), partial, expression, inverted (JSONB, ARRAY, trigram), hash-sharded index (`USING HASH`), statistika (`CREATE STATISTICS`, avtomatik), SQL Activity sahifasi va statement fingerprint, index recommendations, `crdb_internal.cluster_statement_statistics`, hot ranges va ularni yechish

## III bosqich: YugabyteDB va TiDB

10. **YugabyteDB arxitekturasi**: ikki qatlam: YQL (YSQL: PostgreSQL query layer kodining o'zi, shuning uchun PL/pgSQL, triggerlar, ko'p extension ishlaydi; YCQL: Cassandra mos API) va DocDB (RocksDB asosidagi taqsimlangan document store), YB-Master (metadata, tablet joylashuvi) va YB-TServer, tablet va tablet splitting, hash sharding (default, birinchi ustun `HASH`) vs range sharding (`ASC`/`DESC`), colocated tables (kichik jadvallar bitta tablet'da, JOIN tezligi), tablegroup, isolation darajalari (READ COMMITTED, Snapshot, Serializable), xCluster (asinxron klasterlararo replikatsiya) vs synchronous multi-region, read replicas, geo-partitioning, `yugabyted` bilan lokal ishga tushirish, yb_ maxsus funksiyalar va `EXPLAIN (ANALYZE, DIST)`
11. **YugabyteDB amalda: YSQL va YCQL**: PostgreSQL ilovani YugabyteDB'ga ko'chirish (moslik darajasi, sekin ishlaydigan patternlar: sequence cache, `SERIAL` va hotspot, foreign key tekshiruvi tarmoq orqali, katta `IN` ro'yxatlari), stored procedure va trigger YSQL'da (PostgreSQL bilan bir xil sintaksis, lekin taqsimlangan narx), index dizayni (hash vs range, covering `INCLUDE`), YCQL: Cassandra modeli + kuchli consistency (Raft), `TRANSACTIONS` YCQL jadvallarda, TTL, qachon YSQL qachon YCQL, YugabyteDB Voyager bilan migratsiya
12. **TiDB arxitekturasi va HTAP**: komponentlar: TiDB server (stateless SQL layer, MySQL protokoli), TiKV (taqsimlangan transactional KV, RocksDB, Multi-Raft, region'lar), PD (Placement Driver: metadata, scheduling, TSO: global timestamp oracle va uning trade-off'i), TiFlash (columnar replika, Raft learner sifatida real-time sinxron, HTAP), Percolator modeli asosidagi tranzaksiyalar (optimistic vs pessimistic rejim, default pessimistic), `AUTO_RANDOM` va `SHARD_ROW_ID_BITS` hotspot uchun, MySQL bilan moslik va farqlar (stored procedure, trigger, event, FK cheklovlari: hujjatdan joriy holatni tekshirish), `ALTER TABLE ... SET TIFLASH REPLICA 1`, MPP rejimida analitik so'rov, TiDB Dashboard va Key Visualizer, `tiup playground` bilan lokal klaster, TiCDC va TiDB Lightning qisqa

## IV bosqich: Dizayn, performance va tanlov

13. **Taqsimlangan SQL uchun sxema dizayni**: hotspot muammosi: monoton o'suvchi kalitlar (`SERIAL`, `AUTO_INCREMENT`, timestamp) barcha yozishlarni bitta range oxiriga yuboradi, yechimlar: `UUID` (v4 vs v7: tartib va lokallik trade-off), `unique_rowid()`, hash-sharded index (CockroachDB `USING HASH WITH (bucket_count = 16)`), YugabyteDB hash sharding, TiDB `AUTO_RANDOM`, composite primary key ma'lumot lokalligi uchun (tenant_id birinchi), interleaving o'rniga lokallik (Spanner interleave vs CockroachDB eskirgan interleave), sekundar indeks yozish narxi (har indeks boshqa range'da: distributed tranzaksiya), foreign key narxi, sequence o'rniga nima ishlatish, katta tranzaksiyalardan qochish (batch delete/update, `LIMIT` bilan bo'lib)
14. **Distributed query va performance**: so'rov qayerda bajariladi (gateway node va DistSQL/coprocessor push-down), distributed JOIN strategiyalari (lookup join, broadcast, shuffle/hash redistribution), latency manbalari (konsensus yozish, cross-range tranzaksiya, region'lararo RTT, uncertainty restart), `EXPLAIN ANALYZE` da tarmoq vaqti, contention'ni o'lchash, benchmark: `cockroach workload` (`tpcc`, `kv`, `ycsb`), `go-tpc` (TiDB), `ysql_bench`, p50/p99 latency va throughput'ni bitta node PostgreSQL bilan solishtirish, follower reads va stale read bilan o'qishni tezlashtirish, connection pool sozlash (ko'p node'ga yuk taqsimlash, HAProxy)
15. **Middleware sharding: Vitess va Citus bilan solishtirish**: Vitess (MySQL ustida: VTGate, VTTablet, keyspace, VSchema, vindex, resharding, YouTube/Slack/PlanetScale tajribasi), Citus (PostgreSQL extension: coordinator va worker, distributed table `create_distributed_table`, reference table, co-location, distribution column tanlash, Azure Cosmos DB for PostgreSQL), ShardingSphere qisqa, "distributed SQL" vs "sharded SQL" farqi (cross-shard tranzaksiya kafolati, rebalancing avtomatikmi, SQL moslik), qaysi biri qachon, PlanetScale va Neon kabi managed xizmatlar haqida qisqa
16. **Qachon NewSQL kerak va qachon PostgreSQL yetadi**: qaror daraxti: ma'lumot hajmi va yozish throughput (bitta yaxshi PostgreSQL node: o'nlab ming yozish/s, bir necha TB), multi-region active-active va region failure'dan omon qolish talabi, RPO=0 va avtomatik failover, operatsion murakkablik va jamoa tajribasi, latency narxi (har yozish konsensus), SQL va extension moslik (PostGIS, pg_* extension'lar), narx va litsenziya (CockroachDB litsenziya o'zgarishlari, Yugabyte va TiDB Apache 2.0), managed variantlar (CockroachDB Cloud, YugabyteDB Aeon, TiDB Cloud, Spanner, Aurora DSQL haqida qisqa), mavjud ilovani ko'chirish xavflari, real kompaniya case study'lari (blog postlardan), ADR yozish vazifasi (`engineering` uslubidagi qaror hujjati)

## V bosqich: Loyiha

17. **Loyiha: Chaos ostida pul o'tkazish servisi**: 3 node'li CockroachDB (ixtiyoriy: YugabyteDB bilan takrorlash) klasterda hisob va tranzaksiya sxemasi (UUID kalitlar, hotspot'siz), Go yoki Python'da kichik servis (`app/` modulidagi driver va pool bilimi bilan): parallel pul o'tkazish, `40001` retry'ni to'g'ri ishlash, idempotency kaliti; chaos test skripti: node'ni `docker kill`/`docker pause`, tarmoqni uzish (toxiproxy yoki `tc netem` bilan latency/partition), leaseholder'ni ko'chirish; invariant tekshiruvi (umumiy balans o'zgarmaydi, ikki marta yechish yo'q, Jepsen bank testi g'oyasi), natijalar: node yo'qolganda p99 latency va xatolar soni, yozish availability'si, README'da tajriba jurnali va bitta node PostgreSQL bilan solishtirish jadvali

## Ataylab kiritilmagan

Spanner'ni haqiqiy Google Cloud hisobida ishlatish (faqat emulator va konsepsiya), production darajasida Kubernetes operator bilan deploy (CockroachDB/Yugabyte/TiDB operatorlari faqat eslatiladi, `ops/` moduli), har uch bazaning barcha SQL xususiyatlari (faqat taqsimlanganlik bilan bog'liq farqlar), Raft va 2PC nazariyasini qayta yozish (`theory/` da), FoundationDB, Aurora DSQL va boshqa yopiq tizimlar chuqur, Jepsen'ni noldan yozish. Kerak bo'lsa alohida so'rang.

## Mezon

Har mavzu: `main.sql` tanlangan bazada xatosiz ishlaydi, klaster bilan bog'liq vazifalarda (node to'xtatish, region) kuzatilgan natija (`SHOW RANGES`, DB Console skrinshoti o'rniga so'rov natijasi, latency raqamlari) kommentda yozilgan, har dizayn qarorida "nega" izohi (masalan, nega bu kalit hotspot bermaydi). Performance vazifalarida bitta node PostgreSQL bilan solishtirish raqamlari. Loyiha: chaos test skripti qayta ishga tushiriladigan, invariant buzilmagani avtomatik tekshirilgan, README'da natijalar jadvali.
