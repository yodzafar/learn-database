# Ops rejasi: DBA, Database Reliability Engineering va DataOps

Nima uchun alohida: so'rov yozishni bilish va bazani productionda ishonchli ushlab turish boshqa-boshqa kasb. Bazaning eng qimmat nosozliklari SQL sintaksisidan emas, ekspluatatsiyadan keladi: tekshirilmagan backup, jadvalni bloklagan migratsiya, `max_connections` tugashi, disk to'lishi, replika kechikishi, sizib chiqqan parol, sekin so'rov sababli kaskad. Bu modul vendordan mustaqil metodologiya, asboblar va jarayonlarni o'rgatadi: qanday qilib baza bilan bog'liq ishni takrorlanadigan, avtomatlashtirilgan, o'lchanadigan va xavfsiz qilish. Vendorga xos chuqur tafsilotlar (Postgres'da `pg_basebackup` va streaming replication, MySQL'da GTID, MSSQL'da Always On, Oracle'da RMAN va Data Guard) o'z modullarida; bu yerda ular taqqoslanadi va umumiy jarayonga joylashtiriladi.

Boshlash: `theory/` (tranzaksiya, WAL, replication, consensus), `sql/` I–III bosqich, va kamida bitta vendor modulining asosiy qismi (`postgres/` I–IV tavsiya: ko'p mashqlar Postgres'da, keyin MySQL bilan takrorlanadi). Docker va CI (GitHub Actions) asoslari ../learn-devOps dan foydali, K8s mavzulari uchun ../learn-golang yoki ../learn-python VII bosqichi.

Ishlash tartibi: `ops/docs/NN-nom.md` nazariya va vazifalar, kod `ops/NN-slug/` da aralash: `main.sql` (DB ichidagi ish), `main.sh` (backup, restore, benchmark, failover skriptlari, `set -euo pipefail` majburiy), `*.yaml` (docker compose override, Prometheus/Grafana konfiguratsiyasi, K8s manifestlar, GitHub Actions workflow), `migrations/` (Flyway/Liquibase/Atlas fayllari), `runbook.md`/`adr.md`/`postmortem.md` (yozma vazifalar ham vazifa hisoblanadi va tekshiriladi). Tekshiruv `test.sh` (skript natijasini tasdiqlaydi: restore qilingan bazadagi qator soni, migratsiyadan keyingi sxema, metrika endpoint javobi). Ko'p mavzu bir nechta konteynerni birga ko'taradi (`make up db=postgres`, `make up db=mysql`, ba'zida `docker compose -f ops/NN-slug/compose.yaml up`). Buyruqlar: `make ops n=01`, `make ops-test n=01`, `make run d=ops/05-...`, `make check` (`shellcheck`, `sqlfluff`, `squawk`, `yamllint` shu modul uchun).

## I bosqich: DBA roli va arxitektura qarorlari

1. **DBA, DBRE va DataOps**: klassik DBA vazifalari (backup, o'rnatish, tuning, access), Database Reliability Engineering g'oyasi (SRE tamoyillari bazaga: SLO, error budget, toil kamaytirish, "pets vs cattle", infratuzilma kod sifatida, self-service), DataOps va Platform team modeli, DBA va dasturchi o'rtasidagi chegara (kim migratsiya yozadi, kim review qiladi), SLI/SLO bazalar uchun (availability, latency p99, replication lag, RPO/RTO), production'ga yaqin muhit (staging, prod ma'lumot nusxasi va maskalash), ushbu modul uchun lokal laboratoriya: Postgres + MySQL + Prometheus + Grafana docker compose da, `make up` va health check skriptlari
2. **DB tanlash va arxitektura qarorlari (ADR)**: tanlov mezonlari (ma'lumot modeli, konsistentlik talabi, so'rov patternlari, hajm va o'sish, yozish/o'qish nisbati, latency, operatsion murakkablik, jamoa tajribasi, litsenziya va narx, ekotizim, managed variant mavjudligi), "Postgres default" argumenti va qachon undan chiqish kerak, polyglot persistence va uning narxi, ADR formati (Michael Nygard: Context, Decision, Status, Consequences) va MADR, vazifa: uchta real stsenariy (e-commerce katalog, IoT telemetriya, ijtimoiy tarmoq feed) uchun ADR yozish, ilk xatolarni qaytarish narxini baholash (migratsiya xarajati)
3. **Muhitlar, konfiguratsiya va IaC asoslari**: konfiguratsiyani kodda saqlash (`postgresql.conf`/`my.cnf` versiyalash, `ALTER SYSTEM` tuzog'i), konfiguratsiya drift'ini aniqlash, parametrlarni hujjatlash (nega bu qiymat), muhitlar orasidagi farqlarni kamaytirish, docker compose bilan takrorlanadigan muhit, secrets'ni konfiguratsiyadan ajratish (`.env`, Docker secrets, keyin Vault), sxema va ma'lumot ownership, nomlash konvensiyalari va linting qoidalari (jamoa standarti hujjati yozish)

## II bosqich: Schema o'zgarishlari va CI/CD

4. **Schema migratsiya asboblari**: migratsiya modellari (versioned/imperative: Flyway, golang-migrate, Alembic, sqitch; declarative/state-based: Atlas, Liquibase diff, SQL Server SSDT/`sqlpackage`, Prisma Migrate qisman), Flyway (`V1__init.sql`, `R__` repeatable, `flyway_schema_history`, checksum, `baseline`, `repair`, callbacks), Liquibase (changelog XML/YAML/SQL, changeset `id`/`author`, `DATABASECHANGELOG`, `DATABASECHANGELOGLOCK`, preconditions, contexts/labels, `rollback`), Atlas (HCL yoki SQL sxema, `atlas schema diff`, `atlas migrate lint`, migration directory integrity `atlas.sum`), sqitch (dependency-based, `deploy`/`revert`/`verify` uchlik), golang-migrate (`up`/`down`, dirty state), Alembic va Prisma Migrate qisqa (ilova bilan birga), down migratsiya haqidagi bahs (roll-forward afzal), migratsiyani bir xil tarixdan ikki xil DB ga (PG va MySQL) qo'llash vazifasi, migratsiya lock va parallel deploy muammosi
5. **Zero-downtime schema change**: qaysi DDL qaysi lock'ni oladi (Postgres `ACCESS EXCLUSIVE` va lock queue: uzun tranzaksiya ortida `ALTER` hamma so'rovlarni to'xtatishi, `lock_timeout` majburiy; MySQL metadata lock), xavfsiz va xavfli operatsiyalar jadvali (ustun qo'shish default bilan, `NOT NULL` qo'shish, tipni o'zgartirish, index yaratish `CONCURRENTLY`, FK `NOT VALID` + `VALIDATE`, ustunni qayta nomlash), expand/contract (parallel change) patterni bosqichma-bosqich (yangi ustun, dual write, backfill, read switch, eski ustunni o'chirish), katta jadvalni batch bilan backfill qilish (throttling, replika lag'ini kuzatish), online DDL asboblari taqqosi (gh-ost triggersiz binlog asosida, pt-online-schema-change trigger asosida, `pg_repack`, `pg-osc`, MySQL `ALGORITHM=INSTANT`), ilova versiyalari bilan moslik (N va N+1 versiya bir vaqtda ishlaydi), vazifa: yuklama ostida (pgbench) jadvalga zero-downtime o'zgarish va downtime'ni o'lchash
6. **DB uchun CI/CD**: migratsiyani CI'da tekshirish (bo'sh bazaga to'liq qo'llash, production snapshot nusxasiga qo'llash, idempotentlik), SQL linting (`sqlfluff` dialektlar bilan, `squawk` Postgres migratsiya xavfi uchun, `atlas migrate lint`), ephemeral DB (testcontainers, GitHub Actions `services:`, Neon/PlanetScale branching g'oyasi), DB unit testlar (pgTAP, tSQLt, utPLSQL, mytap: vendor modullarda chuqur, bu yerda CI'ga ulash), schema drift aniqlash (prod vs repo), migratsiyani deploy pipeline'ida qaysi bosqichda ishga tushirish (alohida job, init container, ilova startida emas), approval va review jarayoni (DBA review qoidalari, `CODEOWNERS`), GitHub Actions workflow yozish vazifasi: lint + migratsiya + test + drift tekshiruvi
7. **Test ma'lumotlari va seeding**: seed turlari (reference data, fixture, synthetic, prod subset), sintetik ma'lumot generatsiyasi (`generate_series`, Faker, Synth/`dbldatagen` g'oyasi), referential integrity saqlagan holda prod subset olish (Jailer, `pg_dump` + filtr, Tonic/Neosync g'oyasi), deterministik seed (tasodif urug'i), katta hajm testlari uchun ma'lumot hajmini ko'paytirish, seed skriptlarni migratsiyalardan ajratish, personal ma'lumotni testga tushirmaslik (V bosqichdagi maskalash bilan bog'liq)
8. **Upgrade strategiyalari**: minor vs major upgrade, Postgres major upgrade yo'llari (`pg_dump`/restore, `pg_upgrade --link`, logical replication orqali yangi versiyaga ko'chish, blue/green), MySQL (in-place, logical, replika orqali), MSSQL/Oracle qisqa, extension va driver mosligi, upgrade oldidan tekshiruv ro'yxati (deprecated parametrlar, query plan regression, `ANALYZE` keyin), rollback rejasi, managed bazalarda upgrade (RDS Blue/Green Deployments), vazifa: Postgres N dan N+1 ga logical replication bilan minimal downtime upgrade

## III bosqich: Backup, HA va DR

9. **Backup strategiyalari**: RPO va RTO ta'riflari va biznes bilan kelishish, logical vs physical backup (hajm, tezlik, versiya mustaqilligi, granular restore), full/differential/incremental, 3-2-1 qoidasi (va 3-2-1-1-0: immutable va xatosiz tekshirilgan), PITR (base backup + WAL/binlog arxivi), backup asboblari taqqosi (pgBackRest, Barman, WAL-G, XtraBackup, `mydumper`, RMAN, `mongodump`), shifrlash va siqish, object storage'ga (lokal `minio`) yuborish, retention siyosati, backup ham "yashirin ma'lumot sizishi" manbai, vazifa: pgBackRest bilan full + incremental + WAL arxiv va retention
10. **Restore va restore drill**: "tekshirilmagan backup backup emas", restore drill jarayoni va avtomatlashtirish (har kuni boshqa serverga restore, qator soni va checksum taqqoslash, vaqtni o'lchash = haqiqiy RTO), PITR ni aniq vaqtga (`recovery_target_time`) va xato tranzaksiyadan oldingi nuqtaga qilish, bitta jadvalni tiklash usullari, MySQL binlog'dan `mysqlbinlog` bilan aniq pozitsiyagacha, vazifa: "kimdir `DELETE` ni `WHERE` siz bajardi" stsenariysi: PITR bilan tiklash va o'tgan vaqtni o'lchash, runbook yozish
11. **Replication va uni kuzatish**: physical (streaming) vs logical replication, sync vs async vs semi-sync (MySQL), replication lag sabablari (uzun tranzaksiya, katta DDL, replika resurslari, network) va o'lchash (`pg_stat_replication`, `replay_lag`, MySQL `SHOW REPLICA STATUS`, `Seconds_Behind_Source` ning yolg'oni va pt-heartbeat), replication slot'lar va disk to'lish xavfi, read replica'dan o'qishda read-your-writes muammosi, cascading replication, delayed replica (insoniy xatodan himoya), replication buzilganda qayta tiklash, alert qoidalari
12. **HA va failover patternlari**: HA darajalari va "nines" hisobi, failover turlari (manual, automatic), split brain va fencing (STONITH), consensus asosidagi orkestratorlar (Patroni + etcd, MySQL Orchestrator/InnoDB Cluster, MongoDB replica set ichki election), virtual IP vs DNS vs proxy (HAProxy, PgBouncer, ProxySQL) orqali yo'naltirish, client tomonida qayta ulanish va multi-host connection string (`target_session_attrs=read-write`), switchover vs failover, failover paytida ma'lumot yo'qotish (async replika), vazifa: Patroni + etcd + HAProxy 3 node'li klaster, primary'ni o'ldirib failover vaqtini va yo'qolgan tranzaksiyalarni o'lchash
13. **Disaster recovery**: DR stsenariylari (zona, region, ransomware, operator xatosi, korruptsiya), DR arxitekturalari (backup & restore, pilot light, warm standby, active-active), cross-region replication va uning narxi, ma'lumot korruptsiyasini aniqlash (checksums, `amcheck`, `pg_checksums`, `CHECK TABLE`, `DBCC CHECKDB`), DR test (game day) rejalashtirish, DR hujjati va qo'ng'iroq zanjiri, vazifa: DR rejasi hujjati va bitta game day stsenariysi bajarish

## IV bosqich: Observability va performance

14. **Observability: metrikalar va dashboard**: nimani o'lchash (USE: utilization, saturation, errors resurslar uchun; RED: rate, errors, duration so'rovlar uchun; four golden signals), DB ga xos metrikalar (TPS/QPS, connection soni va holati, cache hit ratio, replication lag, lock wait, deadlock, checkpoint, WAL hajmi, bloat, vacuum, disk), `postgres_exporter`, `mysqld_exporter`, `mongodb_exporter`, Prometheus konfiguratsiyasi va PromQL (rate, histogram_quantile), Grafana dashboard (tayyor dashboardlar va o'zingiz yozish), alerting qoidalari (symptom-based, alert fatigue), PMM (Percona Monitoring and Management) va pgwatch qisqa, vazifa: lokal Prometheus + Grafana + ikkita exporter va 5 ta asosiy alert
15. **So'rovlar tahlili: slow log va fingerprinting**: slow query log (Postgres `log_min_duration_statement`, `auto_explain`; MySQL `slow_query_log`, `long_query_time`), statement statistikasi (`pg_stat_statements`, MySQL `performance_schema`/`sys` schema, MSSQL Query Store, Oracle AWR/ASH qisqa), query fingerprinting (literalni normalizatsiya: `pt-query-digest`, `pgBadger`, `pg_stat_statements.queryid`), "top N so'rovlar" (umumiy vaqt bo'yicha, chaqiruv soni bo'yicha, p99 bo'yicha), regressiyani aniqlash, log'larni markazlashtirish (Loki yoki ELK, `elasticsearch/` moduliga bog'lanish), vazifa: sysbench yuklamasi ostida `pt-query-digest` va `pgBadger` hisobotlarini tahlil qilish
16. **Performance tuning metodologiyasi**: metodologiyalar (USE method, wait-based analysis / wait events: Postgres `pg_stat_activity.wait_event`, MySQL `performance_schema.events_waits`, MSSQL `sys.dm_os_wait_stats`, Oracle wait interface), "avval o'lchash" qoidasi, tuning darajalari (so'rov va indeks → sxema → konfiguratsiya → OS → hardware) va har darajaning foyda/narx nisbati, OS darajasi (memory, swappiness, huge pages, I/O scheduler, filesystem, `iostat`/`vmstat`/`pidstat`), konfiguratsiya tuning'ining asosiy parametrlari vendorlar bo'yicha (shared_buffers vs innodb_buffer_pool_size vs max server memory vs SGA), konfiguratsiya generatorlari (PGTune) va ularning cheklovi, tuning eksperiment jurnali yuritish
17. **Capacity planning va benchmarking**: o'sish prognozi (ma'lumot hajmi, TPS, connection), headroom, benchmark turlari (micro vs macro, synthetic vs replay), asboblar (`pgbench` custom skriptlar bilan, `sysbench` OLTP, HammerDB TPROC-C/TPROC-H, YCSB NoSQL uchun, `memtier_benchmark` Redis, `cassandra-stress`), TPC-C va TPC-H tushunchasi (nima o'lchaydi, nega natijalarni taqqoslash qiyin), benchmark tuzoqlari (warm-up, cache, client bottleneck, koordinatsiyalangan qoldirish/coordinated omission, natijani bir marta o'lchash), latency percentile va histogram, vazifa: bir xil yuklamani PG va MySQL'da sysbench bilan o'lchab, metodologiyasi bilan hisobot yozish
18. **Connection management va pooling**: connection narxi (Postgres'da process-per-connection, MySQL thread-per-connection, xotira), `max_connections` ni ko'tarish nega yechim emas, pooler turlari (session, transaction, statement pooling) va har birida nima buziladi (prepared statements, `SET`, advisory lock, temp table), PgBouncer (`pool_mode`, `default_pool_size`, `max_client_conn`, 1.21+ prepared statements qo'llab-quvvatlash), pgcat/Supavisor/Odyssey qisqa, ProxySQL (query routing, read/write split, query rules), pool o'lchamini hisoblash formulasi (yadro soni asosida, HikariCP tavsiyasi) va ilova poolidan pooler'gacha zanjir (`app/` moduliga bog'lanish), connection storm va reconnect, idle in transaction aniqlash va `idle_in_transaction_session_timeout`, vazifa: pgbench 1000 client bilan pooler'siz va PgBouncer orqali solishtirish

## V bosqich: Security va compliance

19. **DB security asoslari**: least privilege (role ierarxiyasi, ilova useri DDL huquqisiz, read-only role, migratsiya useri alohida, `PUBLIC` dan huquqni olish), autentifikatsiya (SCRAM-SHA-256, `pg_hba.conf`, MySQL auth pluginlari, LDAP/Kerberos/IAM auth qisqa), shifrlash in transit (TLS, `sslmode=verify-full`, sertifikat aylanishi) va at rest (TDE: MSSQL/Oracle/MySQL Enterprise, Postgres'da disk darajasi yoki Percona TDE, backup shifrlash), secrets boshqaruvi (Vault dynamic database credentials, AWS Secrets Manager rotation, parolni kodda va log'da saqlamaslik), network izolyatsiya, SQL injection DBA nuqtai nazaridan (parametrlash, minimal huquq zarar hajmini kamaytiradi, `app/` bilan bog'lanish), hardening checklist (CIS Benchmarks), vazifa: Postgres uchun role modeli va hardening skripti
20. **Auditing va compliance**: audit nima uchun (kim, qachon, nimani o'zgartirdi/o'qidi), vendor audit vositalari (pgAudit, MySQL Enterprise Audit / Percona audit plugin, SQL Server Audit, Oracle Unified Auditing), trigger asosidagi audit jadvali va uning cheklovlari, audit log'ni o'zgartirib bo'lmaydigan joyga yuborish, compliance talablari (GDPR: maqsad cheklash, o'chirish huquqi, ma'lumot minimallashtirish; PCI DSS: karta ma'lumotlari, shifrlash, access log; HIPAA: sog'liq ma'lumotlari; SOC 2), "o'chirish huquqi" va backup'lar ziddiyati (crypto-shredding), ma'lumot rezidentligi, vazifa: pgAudit sozlash va audit hisoboti
21. **Data masking va anonimizatsiya**: static masking (prod nusxasini test uchun) vs dynamic masking (so'rov vaqtida: SQL Server Dynamic Data Masking, Oracle Data Redaction, PostgreSQL Anonymizer extension), usullar (substitution, shuffling, nulling, hashing salt bilan, format-preserving encryption, tokenizatsiya, generalization), pseudonymization vs anonymization (GDPR farqi), k-anonymity va re-identification xavfi, referential integrity'ni saqlab maskalash, row-level security bilan multi-tenant izolyatsiya (`app/` dagi multi-tenancy bilan bog'liq), vazifa: prod-ga o'xshash bazadan maskalangan staging nusxasini avtomatik yaratish skripti

26. **Heterogeneous migratsiya**: migratsiya sabablari (litsenziya, cloud, modernizatsiya), bosqichlar (assessment, sxema konvertatsiyasi, ma'lumot ko'chirish, kod (procedura/trigger) konvertatsiyasi, validatsiya, cutover), asboblar (AWS SCT va AWS DMS (full load + CDC), `ora2pg`, `pgloader` (MySQL/MSSQL/SQLite → PG), Babelfish for Aurora PostgreSQL (T-SQL mosligi), Google Database Migration Service, Debezium asosidagi o'z yo'lingiz), tip xaritasi muammolari (Oracle `NUMBER`, `DATE` vaqt bilan, bo'sh string = `NULL`, MSSQL `DATETIME`, `IDENTITY`, collation va case sensitivity), PL/SQL va T-SQL → PL/pgSQL konvertatsiya tuzoqlari (paketlar, autonomous transactions, `MERGE`, xatolarni ushlash), validatsiya (qator soni, checksum, `data-diff`), cutover strategiyalari va rollback, vazifa: `pgloader` bilan MySQL sakila → Postgres va MSSQL namunasi → Postgres, validatsiya skripti bilan

## VII bosqich: Jarayonlar va loyiha

27. **Incident response DB uchun**: tipik DB incidentlari (connection tugashi, disk to'lishi, replika lag, lock zanjiri, runaway query, xotira, XID wraparound, sertifikat muddati), triage birinchi 5 daqiqasi (nima o'zgardi, qaysi so'rov, qaysi lock), tezkor vositalar (`pg_stat_activity` + `pg_blocking_pids`, `pg_cancel_backend`/`pg_terminate_backend`, MySQL `SHOW PROCESSLIST`/`KILL`, `sys.innodb_lock_waits`, MSSQL `sp_whoisactive`), muloqot (incident commander, status sahifa), "avval to'xtat, keyin tushun" vs dalillarni saqlash, vazifa: tayyorlangan 4 ta buzilish stsenariysini (laboratoriyada skript bilan yaratiladi) aniqlash va bartaraf qilish
28. **Runbook, postmortem va on-call**: runbook tuzilmasi (belgi, ta'sir, diagnostika buyruqlari, yechim qadamlari, eskalatsiya, tekshiruv), runbook'ni avtomatlashtirishga aylantirish, blameless postmortem (timeline, root cause va contributing factors, 5 whys cheklovi, action items egasi va muddati bilan), on-call amaliyoti (alert sifati, eskalatsiya, handoff), change management (xavfli o'zgarishlar oynasi, peer review, feature flag'lar), vazifa: 27-mavzudagi stsenariylardan biri uchun runbook va postmortem yozish
29. **DB platforma va self-service**: ichki DB platforma g'oyasi (dasturchi o'zi baza oladi, standartlar avtomatik qo'llanadi), template'lar va golden path, policy as code (OPA/Conftest bilan migratsiya va Terraform tekshiruvi), schema review avtomatlashtirish (bot izohlari: squawk, atlas lint), DB katalogi va ownership, standart dashboard va alert'larni avtomatik ulash, platformani o'lchash (time to provision, migratsiya xato darajasi)
30. **Loyiha: production-ready Postgres platformasi**: docker compose (yoki `kind` + CloudNativePG) da: Patroni (yoki CNPG) bilan 3 node'li HA klaster, PgBouncer, pgBackRest bilan backup va avtomatik restore drill (cron/CI), Prometheus + Grafana + alertlar, pgAudit, role modeli va TLS, Flyway/Atlas migratsiyalari GitHub Actions orqali (lint + test + deploy), zero-downtime migratsiya namoyishi yuklama ostida, failover game day (vaqt va yo'qotish o'lchangan), runbook'lar to'plami va bitta postmortem, README'da arxitektura diagrammasi, SLO va ADR'lar; ixtiyoriy: xuddi shuni MySQL (Orchestrator/InnoDB Cluster + ProxySQL) uchun takrorlash
